## はじめに（リード / 1〜3段落）
- 読者が既にやっていること: 「サブエージェントが便利そうだから、調べ物もリファクタも片っ端から投げている」
- それでも残るストレス: 投げたのに遅くなった・結果が薄い・かえって自分の文脈が分からなくなった

## 最小限の前提（Primer）
- 用語を3つだけ定義: メインエージェント / サブエージェント（Task tool が起動する子エージェント）/ 文脈（コンテキストウィンドウ）
- サブエージェントは独立した文脈を持ち、結果の要約だけを親に返す、という1点だけ押さえる

## 核心のフレーム: サブエージェントは「文脈の隔離装置」である
- 1フレーズで世界観を固定: サブエージェントの本質は「並列実行」より「親の文脈を汚さないこと」
- だから判断は常に「この作業の中間生成物を、親の文脈に残したいか／捨てたいか」で決まる

## サブエージェントを使うべき3つの場面
### 場面1 — 大量の探索で、過程は要らず結論だけ欲しいとき
- いつ: 「この挙動どのファイルで定義されてる?」のような、大量のファイルを読むが最終的に欲しいのは数行の答え
- やること: 探索をサブエージェントに委譲し、要約だけ受け取る / やらないこと: 自分で grep を何十回も回してメインの文脈を読みログで埋める
- コピペ用プロンプト例（探索委譲）

### 場面2 — 独立した複数タスクを並列で回したいとき
- いつ: 互いに依存しない3つの作業（例: 3つのモジュールの調査）を同時に進めたい
- やること: 独立性を確認してから複数サブエージェントを並列起動 / やらないこと: 出力が次の入力になる逐次タスクを無理に並列化する
- コピペ用プロンプト例（並列調査）

### 場面3 — 使い捨ての文脈で本筋を汚したくないとき
- いつ: テストログの解析、長大なエラー出力の切り分けなど、中間生成物が大量だが本筋には残したくない
- やること: 隔離した文脈で処理させ、結論だけ戻す / やらないこと: 巨大ログを直接メインに貼って残りの作業の文脈を圧迫する

## サブエージェントを使わないほうがいい3つの場面
### 反例1 — 親が結果の「過程」を見て次を判断する必要があるとき
- 要約だけ返るので、親が中間状態を握れず、かえって往復が増える
- 失敗例: 設計方針を詰めながら書くコードをサブエージェントに丸投げ → 意図と違う実装が返り、説明し直しで遅くなる

### 反例2 — タスクが小さく、起動コストが見合わないとき
- サブエージェント起動には固定のオーバーヘッドがある
- 失敗例: 1ファイルの1行修正を委譲 → 自分でやれば数秒の作業が往復で数十秒に

### 反例3 — 反復的な対話・微調整が必要なとき
- サブエージェントは一発勝負で、対話の往復ができない
- 失敗例: 「もう少しこう」を繰り返したいUI調整を委譲 → 毎回起動し直しになり対話が成立しない

## 判断フローのまとめ（決断のチェックリスト）
- 1枚に圧縮: ①過程は捨てて結論だけ欲しい? ②独立して並列化できる? ③中間生成物が多く本筋を汚す? → どれかYesなら使う / 過程を見たい・小さい・対話が要る → 使わない

## よくある誤解（FAQ）
- 「並列にすれば速い」→ 並列化の利益は独立タスクのときだけ。依存があると逆効果
- 「サブエージェントの方が賢い結果が出る」→ モデルは同じ。違いは文脈の隔離だけ
- 「常にサブエージェントを使えば文脈を節約できる」→ 起動コストと往復コストで小タスクでは損
- 「サブエージェントの中でさらにサブエージェントを呼べる?」→ caveat として運用上の注意を1行

## おわりに（締め: 価値・感情）
- サブエージェントは万能の高速化ボタンではなく「文脈を守るための投資判断」。この一点で迷いが消え、メインの作業に集中（in the loop）でいられる
