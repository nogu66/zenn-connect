## はじめに

Claude Code のサブエージェント（Task tool）を使い始めると、最初はだいたいこうなります。便利そうだから、調べ物もリファクタも片っ端からサブエージェントに投げる。

でも、しばらくするとおかしなことに気づきます。投げたのに体感では遅くなった。返ってきた結果が薄くて、結局自分で確認し直す。そして一番困るのが、いつの間にか「自分（メインの会話）が今どこまで進んだのか」が分からなくなることです。

この記事で渡したいのは、テクニックではなく**判断基準**です。結論を先に言うと、サブエージェントは「文脈の隔離」と「並列化」のための道具です。それ以外の場面では、サブエージェントに投げるより、素直にメインの会話で進めたほうが速いし、結果もよくなります。読み終えたとき、目の前のタスクを「投げるか／自分で進めるか」その場で判断できる状態をゴールにします。

対象読者は、Claude Code を日常的に使っていて、サブエージェントの存在は知っているが「どこまで任せていいか」で迷っている人です。サブエージェントの設定方法そのものは扱いません。

## 最小限の前提（Primer）

用語を3つだけ揃えておきます。これ以上は要りません。

- **メインエージェント** — あなたが直接やり取りしている会話。作業の本筋を握っている側。
- **サブエージェント** — Task tool が起動する子エージェント。メインとは**独立した文脈**を持ち、仕事を終えると**結果の要約だけ**を親に返して消える。
- **文脈（コンテキスト）** — メインエージェントが保持している会話・コードの履歴。ここが膨らむほど、本筋の作業に使える余地が減る。

押さえるべきは1点だけです。サブエージェントは独立した文脈で動き、過程は捨てて結論だけを親に戻す。この性質が、これから話す判断基準のすべての土台になります。

## サブエージェントの本質は「文脈の隔離」である

サブエージェントの一番の価値は、実は「並列で速くなること」ではありません。**親の文脈を汚さないこと**です。

サブエージェントが大量のファイルを読もうが、長いログを解析しようが、その過程はすべてサブエージェント側の文脈に閉じ込められます。親に返ってくるのは要約だけ。つまりサブエージェントは「文脈の隔離装置」です。

だから判断は、いつも同じ一点に還元できます。**「この作業の中間生成物を、親の文脈に残したいか、それとも捨てたいか」**。残したいならメインで進める。捨てたいならサブエージェントに隔離する。以降の使い分けは、すべてこのフレームの言い換えにすぎません。

## サブエージェントを使うべき3つの場面

### 場面1 — 大量に探索するが、欲しいのは結論の数行だけ

「この挙動ってどのファイルで定義されてるんだっけ?」のように、答えにたどり着くまでに大量のファイルを読む必要があるのに、最終的に欲しいのは数行、というときです。

このとき自分（メイン）で grep を何十回も回すと、ヒットしたコードや読み込んだファイルの中身が、ぜんぶメインの文脈に積み上がります。本筋の作業に戻る頃には、文脈が探索の残骸で埋まっている。これを避けるために、探索ごとサブエージェントへ委譲し、要約だけ受け取ります。

```text
○○という挙動を実装しているファイルと該当行を特定して。
関連する関数のシグネチャだけ要約で返して。
コードの全文は貼らなくていい。
```

数十回の grep に相当する探索を、1回の往復に圧縮できます。やってはいけないのは、過程まで全部メインに残してしまうことです。

### 場面2 — 互いに独立した複数タスクを、並列で回したい

依存関係のないタスクが複数あるとき。たとえば3つのモジュールを別々に調査したい、というケースです。互いに結果を待つ必要がないなら、同時に走らせたほうが当然速い。

```text
以下の3つを並列で調査して。互いに依存はないので同時に進めて構わない。
1. auth モジュールのトークン更新フロー
2. billing モジュールの課金イベント処理
3. notification モジュールの配信リトライ
それぞれ要点を5行以内でまとめて返して。
```

ここで効くのは「並列化の利益は、タスクが本当に独立しているときだけ出る」という条件です。出力が次の入力になるような逐次タスクを無理に並列化すると、後述の反例のように逆効果になります。並列に投げる前に「これらは本当に互いを待たなくていいか?」を一度確認するのが分岐点です。

### 場面3 — 使い捨ての文脈で、本筋を汚したくない

テストログの解析、長大なエラー出力の切り分けなど、**中間生成物は大量に出るが、本筋には残したくない**作業です。

巨大なログを直接メインに貼ると、それだけで文脈を圧迫し、残りの作業に響きます。隔離した文脈で処理させ、「原因はここ」という結論だけを戻させる。場面1と本質は同じで、「過程は捨てて結論だけ欲しい」を、探索ではなく解析に当てはめたものです。

## サブエージェントを使わないほうがいい3つの場面

ここからが、この記事の本題のもう半分です。便利な道具ほど、使わない判断ができることが効いてきます。

### 反例1 — 親が「過程」を見ながら次を判断するとき

サブエージェントは要約しか返しません。だから、過程を見て方針を微調整したい作業とは相性が最悪です。

失敗例。設計方針をまだ詰めている段階で、書くコードをサブエージェントに丸投げする。すると、こちらの意図が固まりきる前に実装が返ってきて、たいてい意図とズレています。説明し直して、また投げて、を繰り返すうちに、自分で書いたほうが速かったとなる。**過程に判断ポイントがある作業は、メインで握り続けるべき**です。

### 反例2 — タスクが小さく、起動コストが見合わないとき

サブエージェントの起動には固定のオーバーヘッドがあります。

失敗例。1ファイルの1行修正をわざわざ委譲する。自分でやれば数秒の作業が、起動と要約の往復で体感数十秒に膨らむ。正確な秒数まで計っていませんが、小さなタスクで「あれ、遅いな」と感じたら、たいていこれです。**作業時間より起動コストのほうが大きいなら、委譲は損**になります。

### 反例3 — 反復的な対話・微調整が必要なとき

サブエージェントは一発勝負です。途中で「もう少しこうして」と対話する余地がありません。

失敗例。UI の見た目を「もうちょっと余白を」「やっぱり色を戻して」と詰めたいのに委譲する。サブエージェントは毎回起動し直しになり、対話が成立しません。**往復しながら詰める作業は、メインの会話でやるほうが速い**です。

## 判断フローのまとめ

迷ったら、この3つを順に自問します。

1. **過程は捨てて、結論だけ欲しいか?**（探索・解析）
2. **独立していて、並列化できるか?**（互いに待たなくていいか）
3. **中間生成物が多く、本筋の文脈を汚すか?**

どれか1つでも Yes なら、サブエージェントに投げる。逆に、**過程を見ながら判断したい・タスクが小さい・対話で詰めたい**のどれかに当てはまるなら、メインで進める。これだけです。

## よくある誤解（FAQ）

**「並列にすればとにかく速くなるのでは?」**
並列化の利益が出るのは、タスクが本当に独立しているときだけです。出力が次の入力になる依存があると、待ち時間が直列に積み上がり、むしろ遅くなります。

**「サブエージェントのほうが賢い結果を返すのでは?」**
モデルは同じです。違いは賢さではなく、文脈が隔離されているかどうかだけ。「サブエージェントだからいい答えが出る」という効果はありません。

**「常にサブエージェントを使えば文脈を節約できるのでは?」**
小さいタスクでは、起動コストと要約の往復のほうが高くつきます。節約になるのは、隔離する中間生成物が十分に大きいときだけです。

**「サブエージェントの中でさらにサブエージェントを呼べる?」**
運用上は、入れ子が深くなるほど親が状況を把握しづらくなります。深いネストは避け、1段で完結する単位に切るのが無難です。

## おわりに

サブエージェントは「とりあえず押せば速くなるボタン」ではありません。**文脈を守るための投資判断**です。投資である以上、見合うときと見合わないときがあります。

「この作業の中間生成物を、親の文脈に残したいか、捨てたいか」。この一点で考えると、投げるか自分でやるかの迷いはほぼ消えます。そして判断が速くなるほど、本筋の作業から意識が離れずに済む——つまり、ずっと in the loop でいられます。

サブエージェントの隔離が効くのは、コンテキストをどう運用するかという、もう一段大きな話の一部です。セッション管理やコンテキスト運用については別記事で扱うので、あわせて参照してください。
