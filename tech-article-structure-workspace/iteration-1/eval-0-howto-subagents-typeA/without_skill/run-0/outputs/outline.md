# 記事構成・アウトライン

## 記事の狙い（一文）

「Claude Code でサブエージェント（Task tool）を使うべきか / 使わないべきか」を、読者が自分の状況に当てはめて判断できる判断基準を提供する。

## 既存記事との差別化

zenn-connect には既に以下の関連記事がある:

- `claude-code-think-abount-skills-and-subagent.md` … **Skills vs SubAgents** の概念的な使い分け
- `code-review-with-subagent-and-skills.md` … Swift コードレビューでの**具体的な実装例**

本記事はこれらと軸をずらす。すなわち「Skills か SubAgents か」ではなく、
**「サブエージェントを使うか、メインスレッドでそのままやるか」** という判断軸に絞る。
読者が抱える本当の悩みは「機能の違い」ではなく「いつ呼べばいいのか分からない / 呼んだら逆に遅くなった」という運用判断であると仮定する。

## 想定読者

- Claude Code を日常的に使っていて、サブエージェント（Task tool）の存在は知っている
- 「便利らしい」と聞いて使ってみたが、効果を実感できない / かえって遅い・噛み合わないことがある
- 「どういうタスクなら呼ぶべきか」のメンタルモデルが欲しい

## 読者が記事を読み終えたときに獲得する判断基準

1. サブエージェントの本質は「コンテキストの分離」であると理解する
2. 「使うべき3条件」と「使わないほうがいい3条件」をチェックリストとして持ち帰る
3. 迷ったときの一行ルール（"会話の文脈を持ち帰る必要があるか？"）を持つ

## 構成（見出しレベル）

### はじめに
- こんな経験ないですか?（フック: 呼んでみたが噛み合わなかった失敗体験）
- この記事で扱うこと / 扱わないこと
- 対象読者

### サブエージェント（Task tool）とは何か — 1分で前提合わせ
- 独立したコンテキストウィンドウを持つ別インスタンスである、という1点に絞る
- 入口（指示）と出口（最終報告のテキスト）しか親と共有しない、という構造図的説明
- ※概念の詳細は既存記事へリンク

### 判断の核心: サブエージェントの本質は「コンテキストの分離」
- メリットの裏返しがデメリットになる、という構造を最初に提示
- 分離が効く = 探索の中間ゴミを親に残したくないとき
- 分離が邪魔 = 親と密に文脈を共有しながら進めたいとき

### 使うべき3つのサイン
1. 探索的で「読み捨て」が大量に出るタスク（大規模な調査・grep 行脚）
2. 並列に独立して走らせられるタスク（複数ファイル/複数観点を同時に）
3. 出力が「結論だけ」でよいタスク（中間過程を親に残す価値が低い）
- 各サインに具体例を1つずつ

### 使わないほうがいい3つのサイン
1. 親との往復・対話が必要なタスク（途中で方針確認したい）
2. 小さくて速いタスク（起動オーバーヘッドのほうが大きい）
3. 親が中間生成物そのものを使いたいタスク（コードの全文・差分の文脈など）
- 各サインに具体例

### 迷ったときの一行ルール
- 「この作業の途中経過を、親の会話に残す必要があるか?」
  - 残す必要がない → サブエージェント向き
  - 残す必要がある → メインスレッド向き

### よくある失敗パターンと処方箋（表）
- 失敗: 大量の調査結果を持ち帰らせたら要約され過ぎた → 出力フォーマットを指定する
- 失敗: 並列で投げたら同じファイルを編集して競合 → 書き込みは並列にしない
- 失敗: 細かい修正を逐一サブエージェント化して遅い → 閾値を決める

### まとめ
- 本質はコンテキスト分離、判断は3条件 + 一行ルール
- おわりに（今後の展望 / X 宣伝 / 参考リンク）
