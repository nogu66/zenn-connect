## はじめに

Claude Code のサブエージェント（Task tool）を使っていて、こんな経験はありませんか?

- 「便利らしい」と聞いて呼んでみたが、効果を実感できなかった
- 調査を任せたら、欲しかった中間情報まで要約されて消えてしまった
- 細かい作業をいちいちサブエージェント化したら、かえって遅くなった

私も最初は「とりあえずサブエージェントに投げる」をやって、何度も噛み合いませんでした。

問題は機能の理解ではなく、**「どういうときに呼ぶべきか」のメンタルモデルがなかったこと**でした。

この記事では、サブエージェントを **「使うべきか / 使わないべきか」** を、自分のタスクに当てはめて判断できる基準を提供します。

### この記事で得られること

- サブエージェントの本質を「コンテキストの分離」という1点で理解できる
- 「使うべき3つのサイン」と「使わないほうがいい3つのサイン」をチェックリストとして持ち帰れる
- 迷ったときに使える一行ルールが手に入る

### この記事で扱わないこと

- サブエージェントの作成手順・設定ファイルの書き方
- Skills とサブエージェントの概念的な違い（別記事を参照）

https://zenn.dev/nogu66/articles/claude-code-think-abount-skills-and-subagent

### 対象読者

Claude Code を日常的に使っていて、サブエージェント（Task tool）の存在は知っているものの、「いつ呼べばいいのか」が掴めていない方を想定しています。

## サブエージェントとは何か — 1分で前提合わせ

判断基準の話に入る前に、最低限の前提だけ合わせておきます。詳しい概念は上にリンクした記事に譲り、ここでは判断に効く1点だけを押さえます。

**サブエージェントは、独立したコンテキストウィンドウを持つ「別インスタンス」です。**

ポイントは、親（メインの会話）とサブエージェントが共有するのは、入口と出口だけだということです。

```text
[親エージェント]
   │  ① 指示を渡す（入口）
   ▼
[サブエージェント]  ← 独立したコンテキストで作業
   │      ・ファイルを大量に読む
   │      ・grep を何度も打つ
   │      ・試行錯誤する
   │  ② 最終報告のテキストだけ返す（出口）
   ▼
[親エージェント]  ← 途中経過は見えていない
```

つまり、サブエージェントが作業中に読んだファイルや打ったコマンドの中身は、**親には残りません**。親が受け取るのは、最後に返ってくる報告テキストだけです。

この「途中経過が親に残らない」という性質が、サブエージェントを使うべきかどうかの判断をすべて決めます。

## 判断の核心: 本質は「コンテキストの分離」

サブエージェントのメリットとデメリットは、実は同じ性質の裏表です。

- **コンテキストが分離される（メリット）**: 探索の途中で出た大量の「読み捨て情報」が親に残らないので、親の会話がスッキリ保たれる
- **コンテキストが分離される（デメリット）**: 親が途中経過を見られないので、密に文脈を共有しながら進めたいタスクには向かない

だから判断は、機能の良し悪しではなく、**あなたのタスクにとって「分離」が得か損か**で決まります。

- 分離が**得**になる = 探索の中間ゴミを親に持ち込みたくないとき
- 分離が**損**になる = 親と文脈を共有しながら進めたいとき

ここから先は、この「得か損か」を具体的なサインに落とし込んでいきます。

## サブエージェントを使うべき3つのサイン

### サイン1: 探索的で「読み捨て」が大量に出るタスク

調査系のタスクは、答えにたどり着くまでに大量のファイルを読み、たくさんの grep を打ちます。その大半は、最終的な答えには不要な「読み捨て情報」です。

これを親のコンテキストでやると、会話が探索ログで埋まり、肝心の作業に使える余白が減ります。サブエージェントに任せれば、探索の残骸はサブエージェント側で消え、親には結論だけが返ってきます。

- 例: 「この大規模リポジトリのどこで認証処理をしているか調べて」
- 例: 「依存しているライブラリのうち、メンテされていないものを洗い出して」

### サイン2: 独立に並列で走らせられるタスク

互いに依存しない作業が複数あるなら、サブエージェントを並列に起動して同時に走らせられます。

- 例: 「3つのモジュールそれぞれについて、テストカバレッジを別々に調べて」
- 例: 「観点A・観点B・観点Cで、同じ設計ドキュメントを別々にレビューして」

ここで重要なのは、**並列にするのは「読み取り中心」のタスクに限る**ことです。書き込みを並列にすると衝突します（後述の失敗パターン参照）。

### サイン3: 出力が「結論だけ」でよいタスク

親が必要としているのが最終的な結論やサマリーだけで、そこに至る過程を親が見る必要がないなら、サブエージェント向きです。

- 例: 「このエラーの原因を特定して、原因と修正方針だけ報告して」
- 例: 「このディレクトリのファイル構成を調べて、要約だけくれ」

## サブエージェントを使わないほうがいい3つのサイン

### サイン1: 親との往復・対話が必要なタスク

途中で方針を確認したい、こまめに相談しながら進めたいタスクは、サブエージェントに向きません。サブエージェントは入口で指示を受け取ったら、出口で報告するまで親と会話できないからです。

- 例: 「実装方針を相談しながら、合意できたら書き進めたい」
- 例: 「途中で出てきた選択肢について、その場で判断を仰ぎたい」

こうしたタスクは、メインスレッドで対話しながら進めるべきです。

### サイン2: 小さくて速いタスク

サブエージェントの起動にはオーバーヘッド（別インスタンスの立ち上げ、指示の受け渡し、報告の往復）があります。数秒で終わる作業をサブエージェント化すると、オーバーヘッドのほうが大きくなり、体感はむしろ遅くなります。

- 例: 「この1ファイルの typo を直して」
- 例: 「この関数の引数を1つ追加して」

こういう作業は、メインスレッドでそのままやったほうが速いです。

### サイン3: 親が中間生成物そのものを使いたいタスク

親が、サブエージェントの作業過程そのもの（読み込んだコードの全文、差分の細部、試行錯誤の文脈）を後続の作業で使いたい場合は、分離がそのまま邪魔になります。

サブエージェントは結論テキストしか返さないので、親は「結論に至った材料」を持っていません。材料が必要なら、最初から親のコンテキストで作業すべきです。

- 例: 「この関数を読み込んで、その内容を踏まえて隣の関数も書き換えたい」（読み込んだ全文を親が使い続ける）

## 迷ったときの一行ルール

3つのサインを毎回思い出すのは大変です。そこで、判断に迷ったときの一行ルールを用意しました。

> **「この作業の途中経過を、親の会話に残す必要があるか?」**

- 残す必要が **ない** → サブエージェント向き（分離が得）
- 残す必要が **ある** → メインスレッド向き（分離が損）

調査の残骸は残したくない（残す必要がない）からサブエージェント。実装方針の議論は残したい（残す必要がある）からメインスレッド。このシンプルな問いで、ほとんどのケースは判断できます。

## よくある失敗パターンと処方箋

実際に使い始めると踏みやすい落とし穴を、処方箋とセットでまとめます。

| 失敗パターン | 何が起きたか | 処方箋 |
| --- | --- | --- |
| 調査を任せたら要約され過ぎた | 欲しかった具体的な行番号やコードが落ちた | 報告の**出力フォーマットを明示**して指示する（例:「該当箇所をファイル名と行番号付きで列挙して」） |
| 並列で投げたら編集が競合した | 複数のサブエージェントが同じファイルを書き換えた | **書き込みを伴うタスクは並列にしない**。並列は読み取り中心に限る |
| 細かい修正を毎回サブエージェント化して遅い | 起動オーバーヘッドが作業時間を上回った | 「**◯秒以上かかりそうな探索だけ**」など、自分の中で閾値を決める |

## まとめ

サブエージェントを使うかどうかの判断は、次の3点に集約されます。

1. **本質はコンテキストの分離**。途中経過が親に残らない、という1点がすべてを決める
2. **使うべきサイン**: 探索的で読み捨てが多い / 独立に並列化できる / 結論だけでよい
3. **使わないサイン**: 親との対話が要る / 小さく速い / 中間生成物を親が使いたい

そして迷ったら一行ルール、**「途中経過を親に残す必要があるか?」** に立ち返ってください。

## おわりに

サブエージェントは「とりあえず投げる」ものではなく、**コンテキストを分離したいときに選ぶ道具**です。この視点を持つと、「なぜか噛み合わない」という体験はかなり減ります。
