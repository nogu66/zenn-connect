## はじめに — 「ツールを生やせば動く」と思っていた

MCP サーバーは「使えそうなツールを定義して並べれば、あとは LLM がいい感じに呼んでくれる」と思っていました。実際に自作してみると、つまずいたのは通信でもプロトコルでもなく、**ツールの設計そのもの**と**認証**でした。

この記事は、MCP サーバーを自分で書いてみて「ツール設計を3回やり直し、認証で何度も詰まった」過程の記録です。MCP の仕様解説ではありません。**これから自作 MCP サーバーを作る人**が、私と同じ穴に落ちないための教訓を、失敗を隠さず並べます。

持ち帰ってほしいのは実装テクニックではなく、**「LLM が自然に使ってくれるツールはどう設計するか」「認証はどこで握るべきか」という制約下の判断**です。

## 前提：MCP サーバーが何かは別記事に逃がす

MCP（Model Context Protocol）そのものの説明は、公式仕様や入門記事に譲ります（【要差し込み：公式ドキュメント／入門記事へのリンク】）。

ここで押さえておけば本記事を読めるのは2点だけです。

- MCP サーバーは **ツール（tool）の一覧とスキーマを LLM に公開する**
- LLM は**ツールの説明文（description）とスキーマを読んで、自分でどれを呼ぶか決める**

この「LLM が自分で選ぶ」が、後のすべての失敗の根っこになります。

## 比喩：MCP サーバーは「LLM のための受付窓口」

MCP サーバーは、LLM のための**受付窓口**だと考えると設計の良し悪しが見えてきます。

受付窓口に求められるのは2つです。**「何を頼めるかが一目でわかること」**（＝ツールの粒度と説明）と、**「本人確認が通っていること」**（＝認証）。窓口の品目が多すぎても少なすぎても客は迷い、本人確認が雑だと別人の用件を処理してしまう。私が壊したのは、まさにこの2点でした。

以降、ツール設計の3回の作り直しと、認証の3つの罠を順に書きます。

## 試行1 — ツールを細かく分けすぎて、LLM が選べなくなった

最初の直感は「ツールは単機能で、細かく分けるほどキレイ」でした。

ユーザー操作を `search_user` / `get_user` / `list_users` / `get_user_profile` / `get_user_settings` …と細分化しました（【要差し込み：実際に切ったツール名の一覧】）。

ところが LLM は**似たツールの間で選択を誤りました**。「ユーザーの情報が欲しい」だけのリクエストに対し、`search_user` を呼んだり `get_user_profile` を呼んだり、ターンごとに選択がブレたのです。

```text
【要差し込み：1ターン分の実ログ】
User: 田中さんの設定を見せて
→ LLM が get_user → get_user_profile の順で2回呼び、settings には辿り着けなかった
```

**なぜダメだったか：** 受付窓口の品目を増やしすぎると、客（LLM）は「どれが自分の用件か」を毎回当てる羽目になる。粒度が細かいほど、説明文の差分が小さくなり、選択が確率的にブレます。

## 試行2 — 1つの巨大ツールに統合したら、引数地獄になった

反省して逆に振り切りました。「ユーザー関連は1ツールにまとめ、`action` 引数で分岐させればいい」。

結果、`user_operation` という1つのツールに `action` / `user_id` / `query` / `fields` / `filter` / `sort` …と引数が【要差し込み：N】個に膨れました。

```json
{
  "name": "user_operation",
  "description": "ユーザーに関するあらゆる操作を行う（action で分岐）",
  "parameters": { "【要差し込み：肥大化したスキーマ全文】": "..." }
}
```

**なぜダメだったか：** description に「あらゆる操作」と書いた時点で、LLM は**いつ呼ぶべきか**を判断できなくなりました。さらに引数の組み合わせが多すぎて、`action` と `fields` の不整合な組み合わせを平気で渡してくる。窓口を1つにした代わりに、申込書の記入欄が地獄になったわけです。

## 試行3 — 「ユースケース単位」で割り直して落ち着いた

最終的に効いたのは、**実装の単位でもデータの単位でもなく、「ユーザーが頼みたいこと」の単位で割る**という基準でした。

`find_users`（検索・一覧をまとめる）/ `get_user_detail`（1人の全情報）/ `update_user_settings` の3つに集約。各ツールの description を「**いつ使うか**」起点で書き直しました。

```text
【要差し込み：description の before / after】
before: "ユーザーを取得する"
after:  "氏名やメールで特定の1人を見つけたいときに使う。複数候補を返す。"
```

評価は「テストが通るか」ではなく、**「モデルが意図どおりのツールを、誤りなく自然に選ぶか」**で測りました（【要差し込み：評価に使ったプロンプト全文とログ】）。試行1で起きた選択ブレが消えたことを確認できて、ようやく設計が落ち着きました。

**含意：** MCP のツールは「機能の最小単位」ではなく「**LLM が選びやすい単位**」で切る。description は仕様書ではなく**「いつ呼ぶか」の道案内**として書く。

## 認証で詰まった話 — 直感 vs 制約

ツール設計が落ち着いた後、本当に時間を溶かしたのは認証でした。ここは時系列ではなく、**エンジニアの直感とシステムの制約の対立**で整理します。

```text
直感:   認証はサーバー側で一度握ってしまえばラク
制約:   MCP クライアントごとに認証コンテキストが違い、
        ローカル開発・マルチユーザー・トークン寿命がそれぞれ別の要求を出す
```

この直感のまま進めて踏んだのが、次の3つの罠です。

### 罠1 — 環境変数で握ったらマルチユーザーで破綻

最初はトークンを環境変数に入れ、サーバー起動時に1回読みました。ローカルでは完璧に動きます。

**なぜダメだったか：** 複数ユーザーが同じサーバーに接続した瞬間に破綻しました。サーバーが握っている認証は1人分なので、**別ユーザーの用件を先頭ユーザーの権限で処理してしまう**（【要差し込み：実際に起きた事故の1ケース】）。受付窓口が、全員を最初の客として扱ってしまった状態です。

### 罠2 — OAuth を入れたらローカル開発の体験が死んだ

罠1を受けて OAuth を導入。マルチユーザーは解決しました。が、**ローカル開発のたびにブラウザ認証フローを通す羽目になり、起動が重くなりました**（【要差し込み：増えた手順数 or 起動秒数、無ければ「体感で明らかに重い」】）。

**トレードオフ：** 認証の正しさと開発体験は綱引きになります。私は最終的に、**ローカルは静的トークン・本番は OAuth** とモードを分けて折り合いをつけました。

### 罠3 — トークンの寿命とツール呼び出しのタイミングがズレた

OAuth にしてもまだ詰まりました。LLM の会話は長く、**最初に取ったトークンが、後半のツール呼び出し時には失効している**ことがある。

```text
【要差し込み：実際のエラーメッセージ全文】
Error: token expired (会話開始から N 分後のツール呼び出しで発生)
```

**設計の答え：** トークンは「セッション開始時に1回」ではなく、**ツール呼び出しの直前に有効性を確認し、必要なら更新する**層を挟みました。

#### 検討したが捨てた案

- **案A：API Gateway を前段に置いて認証を全部寄せる** — インフラが重くなり、ローカル開発で再現できないため却下。
- **案B：ツールごとに個別の認証を持たせる** — 柔軟だが、ツールが増えるたびに認証コードが重複し、罠1の再来になるため却下。

## よくある反論への先回り（FAQ / caveat）

- **「そこまで設計に悩む必要ある？ ツール数個なら直感でいいのでは」** — ツールが3〜4個ならそのとおりです。選択ブレは**似たツールが増えてから**効いてきます。最初から作り込む必要はありません。
- **「MCP の仕様はまだ動く。今これを学んで無駄にならない？」** — 仕様は変わっても、「LLM が選びやすい粒度」「認証をどこで握るか」という**判断の軸は変わりにくい**と考えています。
- **「認証はライブラリに任せれば済むのでは」** — ライブラリは認証フロー自体は解決しますが、**トークン寿命とツール呼び出しのタイミングのズレ**（罠3）は MCP 特有で、自分で層を挟む必要がありました。

## 学んだこと（Lessons Learned）

1. **ツールは機能の最小単位ではなく「LLM が選びやすい単位」で切る。** 細かすぎると選択がブレ、巨大すぎると引数地獄になる（試行1・2）。
2. **description は仕様書ではなく「いつ呼ぶか」の道案内として書く。** before/after で LLM の選択精度が変わる（試行3）。
3. **ツール設計の評価軸は「テストが通るか」ではなく「モデルが自然に正しく選ぶか」。** 実ログで確認する。
4. **認証はサーバーで握りたくなるが、マルチユーザーで破綻する。** ローカルと本番でモードを分けて折り合う（罠1・2）。
5. **トークンの寿命は会話の長さと噛み合わない。** 呼び出し直前に有効性を確認する層を挟む（罠3）。

## おわりに — これは Art であって Science ではない

ここに書いたのは「正解」ではなく、私が3回作り直してたどり着いた**現時点での落としどころ**です。MCP は仕様もエコシステムもまだ動いているので、厳格なルールというより、設計判断のたたき台として読んでもらえればと思います。

同じところで詰まっている人の遠回りが少しでも短くなれば幸いです。MCP の基礎は【要差し込み：前提記事リンク】、関連する設計の話は【要差し込み：関連記事リンク】にまとめています。
