# アウトライン — 自作 MCP サーバーでの試行錯誤を技術記事にする

## 1. 記事タイプとストーリーパターンの判定

- **記事タイプ：B — エンジニアリング教訓（Lessons）**
  理由：渡したいものが「使い方」ではなく「ツール設計をどう直したか・認証でなぜ詰まったか」という制約下の設計思考だから（読み終えた読者が取る行動＝自分の MCP 設計を見直す）。

- **ストーリーパターン：パターン4 — Attempt 連載**
  理由：「ツール設計を何度もやり直した」「認証で詰まった」という時系列の試行錯誤が題材の核であり、失敗を隠さず Attempt を並べる型が最も素直に乗るから。各 Attempt に「なぜダメだったか」を1〜2文で添える。

- 補助：認証の節だけ局所的に **パターン3（直感 vs 制約 → 設計）** を効かせる（「サーバー側で握りたい直感 vs クライアントごとに認証コンテキストが違う制約」）。比喩は1記事1つに抑える（MCP サーバー＝「LLM のための受付窓口」）。

## 2. タイトル案（結論・主張を含む副題つき）

1. **「自作 MCP サーバーでツール設計を3回やり直した話 — 認証で詰まって学んだ設計の勘所」**
2. **「MCP サーバーは『ツールを足す』より『ツールを減らす』ほうが難しい — 試行錯誤の記録」**
3. **「LLM が自然に使ってくれる MCP ツールの作り方 — 失敗した設計と、認証でハマった3つの罠」**

→ 推し：案1（Attempt 連載＝「3回やり直した」が一目で伝わり、認証の痛みも副題に出る）。

## 3. 見出しレベルのアウトライン（各見出し＝何を書くか1行）

```
## はじめに — 「ツールを生やせば動く」と思っていた          ← フック1行 + 読者対象 + 持ち帰り（誰の何を解決するか）
## 前提：MCP サーバーが何かは別記事に逃がす                 ← 基礎は外部リンクへ委譲し、本記事は実戦の教訓に集中する宣言
## 比喩：MCP サーバーは「LLM のための受付窓口」              ← 1記事1比喩で世界観を固定（受付＝何を頼めるかの一覧 + 本人確認）
## 試行1 — ツールを細かく分けすぎて、LLM が選べなくなった   ← 課題→試行→失敗理由（粒度が細かすぎてツール選択が割れた）
## 試行2 — 1つの巨大ツールに統合したら、引数地獄になった     ← 揺り戻しの失敗（パラメータが多すぎ、説明文が破綻）
## 試行3 — 「ユースケース単位」で割り直して落ち着いた        ← 最終解 + 評価軸「モデルが自然に選ぶか」で測った
## 認証で詰まった話 — 直感 vs 制約                          ← パターン3。サーバーで握りたい直感 vs クライアント毎の認証コンテキスト
### 罠1 — 環境変数で握ったらマルチユーザーで破綻             ← なぜダメか1〜2文 + 実際に起きたこと
### 罠2 — OAuth を入れたらローカル開発の体験が死んだ          ← トレードオフの具体例
### 罠3 — トークンの寿命とツール呼び出しのタイミングがズレた  ← 失敗シナリオ1つ
## よくある反論への先回り（FAQ / caveat）                    ← コスト・標準仕様の変化・「そこまで要る?」への先回り
## 学んだこと（Lessons Learned）                            ← 番号付き5点でスキャン用に再掲
## おわりに — これは Art であって Science ではない            ← 謙虚な締め + 関連記事リンク
```
