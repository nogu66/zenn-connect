## はじめに

自作の MCP（Model Context Protocol）サーバーを書いたとき、想像以上にハマりました。ツールの設計を何度もやり直し、認証まわりでも長く詰まりました。

この記事は、その試行錯誤を「過去の自分」に向けて整理したものです。同じ場所で止まっている人が、遠回りをショートカットできれば嬉しいです。

### 想定読者

- これから自作 MCP サーバーを書こうとしている人
- 一度書いてみたが、ツールが LLM にうまく使われず悩んでいる人
- 認証（トークン / OAuth）で接続が通らず詰まっている人

### この記事で扱うこと / 扱わないこと

- 扱う: ツール設計でハマった原因と直し方、認証でハマった原因と直し方、再発防止のチェックリスト
- 扱わない: MCP の仕様の網羅的な解説（公式ドキュメントに譲ります）、特定 SDK の API リファレンス

### 先に結論

僕がハマった原因は、突き詰めると2つでした。

1. ツールの説明文と粒度を「実装者視点」で書いていて、「LLM がいつ使うか」視点で書けていなかった
2. トランスポート（stdio / HTTP）ごとに認証の前提が違うことを理解していなかった

この2点を最初に押さえていれば、やり直しの大半は防げたはずです。

## 前提: MCP サーバーとは何か（最小限）

MCP は、LLM と外部ツール・データソースをつなぐためのプロトコルです。MCP サーバーは「LLM から呼べるツール群」を公開し、クライアント（Claude Desktop や各種 IDE など）がそれを呼び出します。

自作した動機はシンプルで、社内 API を LLM から直接叩きたかったからです。既存の汎用サーバーでは認証や独自エンドポイントに対応しきれず、自前で書くことにしました。

仕様の詳細は公式ドキュメントが充実しているので、ここでは深入りしません。本題は「実装してみて何にハマったか」です。

## ハマりどころ その1: ツール設計を何度もやり直した

### 症状

最初のバージョンでは、こんな現象が起きました。

- LLM がツールをそもそも呼ばない
- 呼んでも引数が間違っている
- 1回で済むはずの処理を何度も呼んでしまう

ツール自体は動くのに、LLM がうまく使ってくれない。これが地味に一番つらかったです。

### なぜ起きたか

原因を振り返ると、3つありました。

**1. ツールの粒度が不適切だった**

最初は「DB を操作する」という1つの巨大なツールに、検索・作成・更新・削除を全部詰め込んでいました。引数 `action` で分岐させる設計です。これだと LLM はどの `action` を選べばいいか判断しづらく、誤呼び出しが頻発しました。

**2. 説明文（description）が実装者視点だった**

`description` を「この DB テーブルを操作します」のように書いていました。LLM が知りたいのは「いつこのツールを使うべきか」なのに、それが書かれていませんでした。

**3. 入力スキーマが曖昧だった**

引数を全部 `string` のオプショナルにしていたため、LLM が何を渡すべきか分からず、空のまま呼んだり余計な引数を付けたりしていました。

### どう直したか

**1ツール=1ユースケースに分割**

巨大ツールを `search_users` / `create_user` / `update_user` のように用途別に分けました。LLM にとって選択肢が明確になり、誤呼び出しが激減しました。

Before:

```typescript
// 何でもできる巨大ツール（LLM が action を選びきれない）
server.tool(
  "manage_users",
  "ユーザーテーブルを操作します",
  {
    action: z.string(), // "search" | "create" | "update" ...
    payload: z.string().optional(),
  },
  async ({ action, payload }) => { /* action で分岐 */ }
);
```

After:

```typescript
// 用途を分け、description は「いつ使うか」を書く
server.tool(
  "search_users",
  "名前またはメールでユーザーを検索したいときに使う。1件特定したい場合も、複数候補を絞り込む場合もこれを使う。",
  {
    // 必須・型・enum を明示して LLM の迷いを消す
    query: z.string().describe("検索キーワード（名前またはメールアドレス）"),
    field: z.enum(["name", "email"]).describe("検索対象のフィールド"),
    limit: z.number().int().min(1).max(50).default(10),
  },
  async ({ query, field, limit }) => {
    const users = await db.searchUsers({ query, field, limit });
    return { content: [{ type: "text", text: JSON.stringify(users) }] };
  }
);
```

ポイントは3つです。

- description に「いつ使うか」を書く（ツールが何をするかではなく）
- 引数に `.describe()` を付けて意味を伝える
- `enum` や `min/max`、`default` で取りうる値を縛る

この書き直しで、ツール設計のやり直しはほぼ止まりました。

## ハマりどころ その2: 認証まわりで詰まった

### 症状

ローカルの単体テストでは動くのに、実際にクライアントから接続すると認証で弾かれる。トークンをどこでどう渡せばいいのかが分からず、長く詰まりました。

### なぜ起きたか

**1. トランスポートで認証の前提が違うことを理解していなかった**

MCP には主に2つのトランスポートがあります。

| トランスポート | 主な用途 | 認証の渡し方 |
| --- | --- | --- |
| stdio | ローカルのプロセス起動 | プロセスの環境変数で渡す |
| HTTP (Streamable HTTP) | リモート接続 | HTTP ヘッダ（Authorization など）で渡す |

僕は HTTP 前提のつもりでヘッダに認証を載せようとしていたのに、クライアント側は stdio で起動していました。stdio では HTTP ヘッダなど存在しないので、当然弾かれます。トランスポートの食い違いが根本原因でした。

**2. シークレットの受け渡し場所を取り違えた**

API キーをコードに直書きしたり、リクエストごとに引数で渡そうとしたりしていました。これはセキュリティ的にも設計的にも筋が悪い方法でした。

### どう直したか

**stdio なら環境変数で渡す**

クライアントの設定でサーバー起動時に環境変数を注入し、サーバーはそれを読むだけにしました。

クライアント設定の例:

```json
{
  "mcpServers": {
    "my-internal-api": {
      "command": "node",
      "args": ["/path/to/server.js"],
      "env": {
        "API_TOKEN": "xxxxxxxx"
      }
    }
  }
}
```

サーバー側:

```typescript
// シークレットは env から読む。引数やコード直書きにしない
const apiToken = process.env.API_TOKEN;
if (!apiToken) {
  throw new Error("API_TOKEN が設定されていません");
}

const apiClient = createClient({ token: apiToken });
```

**HTTP なら Authorization ヘッダで受ける**

リモートで動かす場合は、HTTP トランスポートのリクエストヘッダから検証します。

```typescript
// Streamable HTTP の場合: リクエストヘッダで検証
app.post("/mcp", (req, res) => {
  const auth = req.headers["authorization"];
  if (!auth || !isValidToken(auth)) {
    res.status(401).json({ error: "unauthorized" });
    return;
  }
  // 認証OKなら MCP のリクエスト処理へ
});
```

「自分のクライアントがどのトランスポートで接続しているか」を最初に確認していれば、ここで詰まることはありませんでした。

## 学んだ設計指針

### ツール設計のチェックリスト

- [ ] 1ツール=1ユースケースになっているか（`action` 分岐で詰め込んでいないか）
- [ ] description に「何をするか」ではなく「いつ使うか」を書いたか
- [ ] 各引数に `.describe()` で意味を添えたか
- [ ] 取りうる値を `enum` / `min/max` / `default` で縛ったか
- [ ] 実際に LLM に使わせて、呼ばれ方を観察したか

### 認証のチェックリスト

- [ ] クライアントがどのトランスポート（stdio / HTTP）で接続するか確認したか
- [ ] シークレットを env またはヘッダで渡し、コード直書きやコード混入を避けたか
- [ ] 認証失敗時に分かりやすいエラーを返しているか

### 最初から知りたかったこと

一番の学びは「MCP サーバーの読者は LLM である」という当たり前のことでした。人間向けの API ドキュメントを書く感覚ではなく、LLM が迷わず選べるかを基準に設計する。これに尽きます。

## おわりに

ツール設計のやり直しも認証地獄も、振り返れば「最初の前提確認」を飛ばしたことが原因でした。

- ツールは LLM 視点（いつ使うか）で設計する
- 認証はトランスポートを確認してから組む

今後は、ツールの呼ばれ方を自動で検証するテストや、複数クライアント対応も整えていきたいと考えています。同じところで詰まっている人の遠回りが、少しでも減れば幸いです。
