# 記事アウトライン: 週末に作った Raycast 拡張の紹介

## メタ情報

- **記事タイプ**: プロダクト紹介（個人開発の Raycast 拡張）
- **ゴール**: 読者にインストールして実際に使ってもらう（コンバージョン重視）
- **想定読者**: Raycast を日常的に使っている開発者・パワーユーザー。拡張を探している人。
- **トーン**: 軽量・実用的。週末プロジェクトらしいカジュアルさを残しつつ、信頼感のある説明。

## 設計方針

プロダクト紹介記事で「インストールして使ってもらう」がゴールなので、構成は次の順番を意識する。

1. **30秒で「自分ごと」にさせる** — 冒頭で「こういう不便、ありますよね？」を提示し、読者の課題と一致させる。
2. **何ができるかを一目で見せる** — GIF / スクリーンショットを早い段階に置く（手を動かす前に価値を理解させる）。
3. **インストール導線を摩擦なく** — Store リンク + コマンド。詰まりやすい箇所を先回りで潰す。
4. **使い方を最短ルートで** — まず「これだけやれば動く」を示し、応用は後段に。
5. **最後に背中を押す** — フィードバック歓迎・GitHub・今後の予定でコミュニティ感を出す。

CTA（Call To Action = インストールリンク）は「課題提示の直後」と「使い方の後」の2か所に置き、離脱ポイントをカバーする。

## 目次（見出し構成）

### タイトル案
- 「週末に作った Raycast 拡張『〇〇』で、〜の手間をゼロにする」
- 問題と手段の両方をタイトルに含める（CLAUDE.md のガイドラインに準拠）

### 1. はじめに
- どんな人に向けた記事か（Raycast ユーザー / 〜の作業をしている人）
- この記事で分かること（拡張でできること・入れ方・使い方）
- 週末に作ったというカジュアルな背景を一言

### 2. こんな課題、ありませんか？（フック）
- 既存ワークフローの不便さを具体例で描写
- 「自分も同じことをしていた」と共感を得る
- ここで拡張の価値を一文で宣言

### 3. 何ができるのか（デモ）
- スクリーンショット / GIF で動作を見せる
- 主要機能を3つ程度に絞って箇条書き
- ここに1つ目の CTA（Store リンク）

### 4. インストール方法
- Raycast Store からの導入手順（最短）
- 前提条件（Raycast のバージョン、API キーが必要なら明記）
- コマンドからの導入 / 手動ビルドの補足

### 5. 使い方（最短ルート）
- 「まずこれだけ」で動く手順を step で
- 主要コマンドの説明とスクリーンショット
- よく使う設定（Preferences）の紹介

### 6. ちょっとした工夫・実装の裏側（任意・軽め）
- 開発で工夫した点を1〜2個だけ
- 技術記事としての厚みを出すが、長くしすぎない

### 7. 既知の制約と今後の予定
- 現状できないこと（誠実に書くと信頼が上がる）
- ロードマップ・募集中の機能要望

### 8. おわりに
- まとめ（誰のどの課題を解決するか再掲）
- 2つ目の CTA（インストール + GitHub スター + フィードバック導線）
- 謝辞
