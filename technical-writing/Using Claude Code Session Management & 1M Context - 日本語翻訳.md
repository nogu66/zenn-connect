# Claude Code の使い方: セッション管理と 100万トークンコンテキスト

> 原文: [[Using Claude Code Session Management & 1M Context]]

![画像](https://pbs.twimg.com/media/HF-p1RUbEAIH-6t?format=jpg&name=large)

最近の Claude Code ユーザーとの対話で繰り返し出てくるテーマのひとつが、**100万トークンのコンテキストウィンドウは諸刃の剣**だということです。

長時間の自律動作やタスクの信頼性向上には役立ちますが、セッションを意図的に管理しないと**コンテキスト汚染**を招きやすくなります。

セッション管理の重要性はこれまで以上に高まっており、関連する疑問も多いようです。ターミナルでセッションを1つ開きっぱなしにするのか、2つにするのか。プロンプトのたびに新規セッションにするのか。いつ `compact`、`rewind`、サブエージェントを使うべきか。悪いコンパクトは何が原因か。

ここには意外と細かい点が多く、Claude Code の体験を大きく左右します。ほとんどは**コンテキストウィンドウの管理**から生じます。

## コンテキスト・コンパクト・コンテキスト腐敗の要点

![画像](https://pbs.twimg.com/media/HF-nqWCbEAE3Oan?format=jpg&name=large)

コンテキストウィンドウとは、次の応答を生成するときにモデルが一度に「見える」すべての情報のことです。システムプロンプト、これまでの会話、すべてのツール呼び出しとその出力、読み込まれたすべてのファイルが含まれます。Claude Code のコンテキストウィンドウは**100万トークン**です。

残念ながらコンテキストを使うにはわずかなコストがあり、これを**コンテキスト腐敗（context rot）**と呼ぶことが多いです。コンテキスト腐敗とは、コンテキストが増えるとモデル性能が低下するという観察で、注意がより多くのトークンに分散し、古くて無関係な内容が現在のタスクから注意をそらし始めるためです。100万トークンのモデルでは、**おおよそ 30万〜40万トークン**あたりからある程度のコンテキスト腐敗が起きますが、タスク依存性が高く、厳密なルールではありません。

コンテキストウィンドウには上限があるため、上限に近づくと、これまでの作業をより小さな要約に圧縮し、新しいコンテキストウィンドウで作業を続ける必要があります。これを**コンパクト（compaction）**と呼びます。自分でコンパクトをトリガーすることもできます。

![画像](https://pbs.twimg.com/media/HF-ntaxboAAZuCm?format=jpg&name=large)

## すべてのターンは分岐点

Claude に何かを依頼して終わったとします。コンテキストには（ツール呼び出し、ツール出力、あなたの指示など）情報が入っており、次に何をするかについて、意外と多くの選択肢があります。

- **続行（Continue）** — 同じセッションで別のメッセージを送る
- **/rewind（Esc を2回）** — 以前のメッセージに戻り、そこからやり直す
- **/clear** — 新しいセッションを開始する（多くの場合、直前で得た知見を要約したブリーフを添えて）
- **Compact** — これまでのセッションを要約し、その要約の上で続ける
- **サブエージェント** — 次の作業を別コンテキストのエージェントに任せ、結果だけ親に戻す

最も自然なのは続行ですが、他の4つはコンテキスト管理のために用意されています。

![画像](https://pbs.twimg.com/media/HF-n6mMbEAEImhv?format=jpg&name=large)

## いつ新しいセッションを始めるか

100万トークンのコンテキストにより、フルスタックアプリをゼロから構築するなど、より長いタスクをより信頼して任せられるようになりました。しかし、モデルがコンテキスト切れしていなくても、**新しいセッションを始めるべき場面**はあります。

一般的な目安は、**新しいタスクを始めるときは、新しいセッションも始める**ことです。

グレーゾーンは、一部のコンテキストはまだ必要だが全部は不要、という関連タスクです。

例えば、実装したばかりの機能のドキュメントを書く場合。新しいセッションでもよいですが、Claude は実装したファイルを読み直す必要があり、遅くコストもかかります。ドキュメント作成は高度な推論がそれほど必要でないタスクかもしれないので、関連ファイルを再読みしない効率の方が、余分なコンテキストのコストに見合うことが多いです。

## 訂正より rewind

![画像](https://pbs.twimg.com/media/HF-oDqjbEAI94h5?format=jpg&name=large)

コンテキスト管理がうまい人の習慣をひとつ挙げるなら、**rewind** です。

Claude Code では Esc を2回押す（または `/rewind` を実行する）と、任意の以前のメッセージに戻り、そこから再プロンプトできます。その時点以降のメッセージはコンテキストから落ちます。

rewind は、しばしば訂正より良いアプローチです。例えば Claude が5ファイルを読み、ある方針を試して失敗したとします。「うまくいかなかった、代わりに X を試して」と打ちたくなるかもしれませんが、より良いのは**ファイル読み込みの直後に rewind し、学んだことを踏まえて再プロンプト**することです。「アプローチ A は使わないで。foo モジュールはそれを公開していない — いきなり B に進んで。」

「ここから要約して（summarize from here）」を使えば、Claude に学びを要約させ、引き継ぎメッセージを作れます。何かを試してうまくいかなかった未来の自分から、以前のイテレーションの Claude へのメッセージのようなものです。

![画像](https://pbs.twimg.com/media/HF-oKwBbEAAdb6I?format=jpg&name=large)

## コンパクト vs 新規セッション

セッションが長くなると、重さを減らす方法は2つあります。`/compact` か `/clear`（して新規開始）です。似ていますが、挙動は大きく異なります。

**Compact** は、これまでの会話をモデルに要約させ、履歴をその要約で置き換えます。**情報が失われる（lossy）** 処理で、何が重要だったかを Claude に任せますが、自分で書く必要はなく、重要な学びやファイルをより丁寧に含めてくれることもあります。指示を渡して誘導できます（例: `/compact focus on the auth refactor, drop the test debugging`）。

![画像](https://pbs.twimg.com/media/HF-oPtxaAAAUKMr?format=jpg&name=large)

`/clear` では、自分で重要なことを書き出します（「auth ミドルウェアをリファクタ中、制約は X、重要なファイルは A と B、方針 Y は却下済み」など）とクリーンに始めます。手間は増えますが、結果のコンテキストは**自分が relevant と判断した内容だけ**になります。

## 悪いコンパクトの原因は？

![画像](https://pbs.twimg.com/media/HF-oy22bEAE_Jd8?format=jpg&name=large)

長時間セッションを多用していると、コンパクトが特にまずいときがあることに気づいたことがあるかもしれません。よくあるのは、**モデルが作業の方向性を予測できないとき**に悪いコンパクトが起きるケースです。

例: 長いデバッグのあとオートコンパクトが発火し、調査が要約される。次のメッセージは「さっき [bar.ts](http://bar.ts/) で見たあの別の警告も直して」。

しかしセッションはデバッグ中心だったため、**別の警告は要約から落ちている**かもしれません。

これは特に難しく、コンテキスト腐敗のため**コンパクト時点ではモデルが最も知性が低い**からです。100万コンテキストがあれば、次に何をするかの説明を添えて**先回りで `/compact` する**余裕が増えます。

## サブエージェントと新しいコンテキストウィンドウ

![画像](https://pbs.twimg.com/media/HF-o6v1bQAA7pS6?format=jpg&name=large)

サブエージェントはコンテキスト管理の一形態で、作業の一部が大量の中間出力を生み、それを二度と必要としないことがわかっているときに有効です。

Claude が Agent ツール経由でサブエージェントを起動すると、そのサブエージェントは**独自の新しいコンテキストウィンドウ**を得ます。必要なだけ作業し、最終レポートだけを親に返せます。

私たちが使う心のテストは、**このツール出力をまた必要になるか、結論だけでよいか**です。

Claude Code は自動でサブエージェントを呼びますが、明示的に指示した方がよい場合もあります。例えば:

- 「この仕様ファイルに基づき、この作業結果を検証するサブエージェントを立ち上げて」
- 「別コードベースを読み、auth フローの実装を要約するサブエージェントを切り離し、同じやり方で自分でも実装して」
- 「git の変更に基づき、この機能のドキュメントを書くサブエージェントを切り離して」

## まとめ

要するに、Claude が1ターンを終え、新しいメッセージを送ろうとするとき、そこは**意思決定の分岐点**です。

将来的には Claude がこれをある程度自動で扱うようになると期待していますが、今は**Claude の出力を導く方法のひとつ**として、セッション管理があります。
