# Claude Code 構築の教訓: エージェントの目で見る

> 原文: [[Lessons from Building Claude Code Seeing like an Agent]]

エージェントハーネス構築で最も難しい部分のひとつは、**アクション空間**の設計です。

Claude はツール呼び出しで動きますが、Claude API では bash、スキル、最近のコード実行など、ツールの作り方は複数あります（プログラム的ツール呼び出しは [@RLanceMartin の新記事](https://x.com/RLanceMartin/status/2027450018513490419) を参照）。

これらの選択肢の下で、エージェントのツールをどう設計するか。コード実行や bash だけで足りるか。ユースケースごとに50個のツールが必要か。

難しい数学問題を渡されたとき、自分に欲しいツールは何か——それは自分のスキル次第です。

紙は最低限ですが手計算に限界があります。電卓は良いですが高度な機能の使い方を知る必要があります。最速・最強はコンピュータですが、コードを書いて実行する方法を知っている必要があります。

これはエージェント設計の有用なフレームです。**モデル自身の能力に合った形のツール**を与えたい。しかしその能力はどう知るか。出力に注意を払い、実験する。**エージェントの目で見る**ことを学ぶ。

Claude Code を作りながら注意して学んだ教訓です。

## エリシテーションと AskUserQuestion ツールの改善

AskUserQuestion ツールの目標は、Claude の質問能力（エリシテーション）を高めることでした。

プレーンテキストでも質問はできますが、答えるのに不要な時間がかかる感じがありました。ユーザーと Claude の間の通信帯域をどう広げるか。

### 試行1 — ExitPlanTool の編集

最初は ExitPlanTool に質問配列パラメータを足しました。実装は最も簡単でしたが、プランとプランに関する質問セットを同時に求めるため Claude を混乱させました。ユーザーの回答がプランと矛盾したら？ ExitPlanTool を二度呼ぶ必要がある？ 別アプローチが必要でした。

（ExitPlanTool を作った理由は [プロンプトキャッシュの記事](https://x.com/trq212/status/2024574133011673516) を参照）

### 試行2 — 出力形式の変更

次に出力指示を少し変えた Markdown で質問するよう試しました。箇条書きで、代替を括弧で示す形式など。最も一般的な変更で、Claude もそれなりに出力しましたが保証はありません。余計な文を足したり、選択肢を省略したり、別形式を使ったりします。

### 試行3 — AskUserQuestion ツール

最終的に、いつでも呼べるツールを作りました。特に plan mode 中に呼ぶようプロンプトします。ツール発火時はモーダルで質問を表示し、ユーザーが答えるまでエージェントループをブロックします。

構造化出力をプロンプトでき、複数選択肢をユーザーに与えやすくなりました。Agent SDK やスキルから参照するなど、ユーザーがこの機能を合成できます。

最も重要なのは、**Claude がこのツールを呼ぶのが好き**で、出力がうまくいくこと。最高の設計でも Claude が呼び方を理解しなければ意味がありません。

Claude Code におけるエリシテーションの最終形かは不明です。次の例のように、あるモデルに効くものが別モデルでは最適でないこともあります。

## 能力の更新 — Tasks と Todos

Claude Code 初版では、モデルが軌道に乗るために Todo リストが必要だと気づきました。TodoWrite ツールで書き、作業しながらチェックオフし、ユーザーに表示しました。

それでも Todo を忘れることが多く、5ターンごとにシステムリマインダーで目標を思い出させました。

しかしモデルが改善するにつれ、リマインダーは不要になり、むしろリストに縛られると誤解させることがありました。Opus 4.5 はサブエージェントが格段に上手くなりましたが、共有 Todo リストでサブエージェントはどう協調するか。

これを見て TodoWrite を Task ツールに置き換えました（[Tasks の記事](https://x.com/trq212/status/2014480496013803643)）。Todo は軌道維持、Task はエージェント間通信。依存関係、サブエージェント間更新、変更・削除が可能です。

**モデル能力が上がると、かつて必要だったツールが制約になる**ことがあります。必要ツールについての前提を常に見直すことが重要です。似た能力プロファイルの少数モデルに絞ってサポートするのも有用です。

## 検索インターフェースの設計

Claude にとって特に重要なツール群は、**自分用のコンテキストを構築する検索ツール**です。

初期の Claude Code は RAG ベクトルDBでコンテキストを渡していました。強力・高速ですがインデックスとセットアップが必要で、環境によって壊れやすい。より重要なのは、Claude が自分でコンテキストを見つけられなかったこと。

Web 検索できるなら、コードベースも検索できるはず。Grep ツールでファイルを探し、コンテキストを自分で構築させました。

**Claude が賢くなるほど、適切なツールがあればコンテキスト構築が上手くなる**というパターンです。

Agent Skills 導入時に **progressive disclosure** を形式化しました。エージェントが探索で段階的に関連コンテキストを発見します。

スキルファイルを読み、そこから他ファイルを再帰的に読む。スキルで API の使い方や DB クエリ手順を足す用途も一般的です。

1年で、コンテキストをほとんど構築できなかった状態から、複数層のファイルをネスト検索して必要なコンテキストに辿り着くまで進化しました。

progressive disclosure は、ツールを増やさず機能を足す一般的な技法です。

## Progressive Disclosure — Claude Code Guide エージェント

Claude Code は現在約20ツールがあり、常に「全部必要か」と問います。新ツールのハードルは高く、モデルが考える選択肢が1つ増えます。

Claude が Claude Code の使い方を十分知らないことに気づきました。MCP の追加方法やスラッシュコマンドの説明を聞いても答えられませんでした。

すべてをシステムプロンプトに入れることもできましたが、ユーザーはめったに聞かないためコンテキストロットになり、本業（コードを書くこと）を妨げます。

代わりに progressive disclosure を試しました。ドキュメントへのリンクを渡し、読み込んで検索させました。動きましたが、正解に必要なのは答えだけなのに大量の結果をコンテキストに載せがちでした。

そこで **Claude Code Guide サブエージェント**を作りました。Claude 自身について聞かれたときに呼ばれ、ドキュメント検索の詳細指示と返すべき内容を持ちます。

完璧ではなく、セットアップ方法を聞くとまだ混乱することもありますが、以前よりずっと良いです。**ツールを増やさず**アクション空間を広げられました。

## 科学ではなく芸術

ツール構築の厳密なルール集を期待していたなら、残念ながらこのガイドはそれではありません。モデルのツール設計は科学であると同時に**芸術**です。使うモデル、エージェントの目的、動く環境に強く依存します。

よく実験し、出力を読み、新しいことを試してください。**エージェントの目で見てください。**
