# Using Claude Code: セッション管理と 1M コンテキスト

> 原文: [[Using Claude Code Session Management & 1M Context]]

最近の Claude Code ユーザーとの対話で繰り返し出てくるテーマがあります。100万トークンのコンテキストウィンドウは**諸刃の剣**だということです。

長時間の自律動作やタスクの信頼性向上には効きますが、セッションを意図的に管理しないとコンテキスト汚染の入り口も開きます。

セッション管理はこれまで以上に重要で、compact・rewind・サブエージェントなどについての質問も多いです。ターミナルで1セッションを開き続けるか、プロンプトごとに新規か。compact・rewind・サブエージェントはいつ使うか。悪い compact の原因は何か。

ほとんどすべてがコンテキストウィンドウの管理から来ており、細部が Claude Code の体験を大きく左右します。

## コンテキスト・コンパクション・コンテキストロットの要点

コンテキストウィンドウは、次の応答を生成するときにモデルが一度に「見える」すべてです。システムプロンプト、これまでの会話、各ツール呼び出しと出力、読み込んだファイルを含みます。Claude Code のコンテキストウィンドウは100万トークンです。

残念ながらコンテキスト利用にはわずかなコストがあり、**コンテキストロット**と呼ばれることが多いです。コンテキストが増えると注意が分散し、古く無関係な内容が現在のタスクから注意を奪い、性能が低下するという観察です。1M モデルではおおよそ 30〜40万トークン付近から起き始めますが、タスク依存で厳密な法則ではありません。

コンテキストウィンドウには上限があるため、上限に近づくとこれまでの作業を要約して新しいウィンドウで続ける必要があり、これを**コンパクション**と呼びます。自分でコンパクションをトリガーすることもできます。

## 毎ターンが分岐点

Claude に何かを頼み終わった直後、コンテキストにはツール呼び出し・出力・指示などが入っています。次に取れる選択肢は意外と多いです。

- **Continue** — 同じセッションで次のメッセージを送る
- **/rewind (esc esc)** — 以前のメッセージに戻り、そこからやり直す
- **/clear** — 新セッションを開始（多くは直前の学びを要約した brief を添えて）
- **Compact** — これまでの会話を要約し、その要約の上で続ける
- **Subagents** — 次の作業をクリーンなコンテキストのエージェントに任せ、結果だけ親に戻す

最も自然なのは continue ですが、他の4つはコンテキスト管理のための手段です。

## 新しいセッションを始めるタイミング

1M コンテキストにより、フルスタックアプリを一から構築するような長いタスクをより信頼して任せられます。しかしモデルがコンテキスト切れしていなくても、新セッションを始めるべきときはあります。

一般的な目安は、**新しいタスクを始めるときは新しいセッションも始める**ことです。

グレーゾーンは、一部のコンテキストだけまだ必要な関連タスクです。例: 実装した機能のドキュメント作成。新セッションでも可能ですが、実装ファイルを読み直すのは遅く高コスト。ドキュメントは高度な知性を要しないことが多く、再読の効率のため余分なコンテキストは許容しやすいです。

## 訂正より rewind

良いコンテキスト管理の習慣を一つ選ぶなら、**rewind** です。

Claude Code では Esc を二回（または `/rewind`）で任意の以前のメッセージに戻り、そこから再プロンプトできます。その後のメッセージはコンテキストから落ちます。

訂正の多くは rewind の方が適しています。例: 5ファイルを読み、あるアプローチを試して失敗。「うまくいかなかった、X を試して」と打つより、ファイル読み込み直後に戻り、学びを込めて再プロンプトする。「アプローチ A は使うな。foo モジュールはそれを公開していない——B に直行して」。

「ここから要約」で学びをまとめ、未来の自分が試して失敗したことを伝える handoff メッセージを作ることもできます。

## コンパクション vs 新規セッション

セッションが長くなると、重さを減らす方法は `/compact` と `/clear`（新規）の二つです。似ていますが挙動は大きく異なります。

**Compact** はこれまでの会話をモデルに要約させ、履歴をその要約に置き換えます。ロッシーで、何が重要だったかを Claude に任せますが、自分で書く必要はなく、学びやファイルを漏れなく含めやすい場合もあります。指示も渡せます（`/compact focus on the auth refactor, drop the test debugging`）。

**/clear** では自分で重要事項を書きます（「auth ミドルウェアをリファクタ中、制約は X、重要ファイルは A と B、アプローチ Y は却下」）とクリーンに始めます。手間は増えますが、コンテキストは自分が relevant と判断した内容になります。

## 悪い compact の原因

長時間セッションを多く走らせていると、compact が特に悪いときがあることがあります。よくあるのは、**作業の方向をモデルが予測できない**ときです。

例: 長いデバッグのあとオートコンパクトが発火し、調査が要約される。次のメッセージが「さっき [bar.ts](http://bar.ts/) で見た別の警告を直して」。

セッションがデバッグ中心だったため、別の警告が要約から落ちた可能性があります。

コンテキストロットのため、compact 時はモデルが最も知性が低いタイミングでもあります。1M コンテキストでは、これから何をするかを説明しつつ**先に** `/compact` する余裕が増えます。

## サブエージェントと新しいコンテキストウィンドウ

サブエージェントはコンテキスト管理の一形態で、途中出力を大量に生み、あとで不要になる作業に向いています。

Agent ツールでサブエージェントを起動すると、**新しいクリーンなコンテキスト**が与えられます。必要なだけ作業し、最終レポートだけ親に返せます。

使う判断基準: **このツール出力をまた必要になるか、結論だけでよいか？**

Claude Code は自動でサブエージェントを呼びますが、明示的に指示することも有効です。例:

- 「次の spec に基づき、この作業結果を検証するサブエージェントを立てて」
- 「別コードベースを読み auth フローの実装を要約させ、同じように自分で実装して」
- 「git の変更からこの機能のドキュメントを書くサブエージェントを立てて」

## まとめ

Claude がターンを終え、新しいメッセージを送ろうとするとき、そこは**決断点**です。

将来的には Claude がこれをある程度自動で扱うことを期待していますが、今は出力を導く方法のひとつがセッション管理です。
