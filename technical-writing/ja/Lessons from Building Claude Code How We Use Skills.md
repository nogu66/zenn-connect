# Claude Code 構築の教訓: スキルの使い方

> 原文: [[Lessons from Building Claude Code How We Use Skills]]

スキルは Claude Code で最も使われる拡張ポイントのひとつになりました。柔軟で作りやすく、配布も簡単です。

しかしその柔軟さゆえに、何が最適かわかりにくいこともあります。どんなスキルを作る価値があるか。良いスキルの秘訣は何か。いつ他者と共有するか。

Anthropic 内では数百のスキルを活発に使っています。開発を加速するうえで学んだ教訓です。

## スキルとは

スキルに不慣れなら [ドキュメント](https://code.claude.com/docs/en/skills) や [Agent Skills 入門コース](https://anthropic.skilljar.com/introduction-to-agent-skills) を参照してください。本記事はある程度スキルに慣れている前提です。

よくある誤解はスキルが「ただの markdown ファイル」だということです。最も面白いのはテキストだけではない点です。スキルは**フォルダ**で、スクリプト・アセット・データなどを含み、エージェントが発見・探索・操作できます。

Claude Code のスキルには [多様な設定オプション](https://code.claude.com/docs/en/skills#frontmatter-reference) があり、動的フックの登録も可能です。

最も面白いスキルは、これらの設定とフォルダ構造を創造的に使っています。

## スキルのタイプ

社内のスキルを棚卸しすると、いくつかのカテゴリに集まります。良いスキルは1つにきれいに収まり、複数にまたがると混乱しがちです。決定的なリストではありませんが、組織内で欠けている型を考えるのに有用です。

### 1. ライブラリ・API リファレンス

ライブラリ・CLI・SDK の正しい使い方。社内ライブラリや Claude がつまずく一般的ライブラリ向け。参照コードスニペットのフォルダと、スクリプト作成時の gotchas リストを含むことが多いです。

**例:**

- billing-lib — 社内課金ライブラリのエッジケース・落とし穴
- internal-platform-cli — 内部 CLI ラッパーの全サブコマンドと使い分け
- frontend-design — デザインシステムに合わせて Claude を強化

### 2. プロダクト検証

コードが動くことをどうテスト・検証するか。Playwright、tmux など外部ツールと組み合わせることが多いです。

検証スキルは Claude の出力が正しいことを保証するうえで極めて有用です。検証スキルを1週間かけて磨く価値があることもあります。

出力の動画記録、各ステップでの状態のプログラム的アサーションなど。スキル内に各種スクリプトを含める手法もあります。

**例:**

- signup-flow-driver — サインアップ→メール確認→オンボーディングをヘッドレスブラウザで、各ステップで状態アサート
- checkout-verifier — Stripe テストカードでチェックアウト UI を操作し、請求状態を検証
- tmux-cli-driver — TTY が必要な対話 CLI テスト向け

### 3. データ取得・分析

データ・モニタリングスタックへの接続。認証付きデータ取得ライブラリ、ダッシュボード ID、一般的ワークフロー手順を含むことが多いです。

**例:**

- funnel-query — サインアップ→アクティベーション→課金に必要なイベント結合と canonical user_id テーブル
- cohort-compare — コホート比較、有意差フラグ、セグメント定義へのリンク
- grafana — datasource UID、クラスタ名、問題→ダッシュボード対応表

### 4. ビジネスプロセス・チーム自動化

反復ワークフローを1コマンドに。他スキルや MCP に依存することもあります。ログに過去結果を残すと一貫性と振り返りに役立ちます。

**例:**

- standup-post — チケット・GitHub・過去 Slack を集約→フォーマット済みスタンドアップ（差分のみ）
- create-<ticket-system>-ticket — スキーマ強制と作成後ワークフロー
- weekly-recap — マージ PR・クローズチケット・デプロイ→週次まとめ

### 5. コード足場・テンプレート

特定機能向けのボイラープレート生成。自然言語要件がコードだけではカバーできない足場に特に有用です。

**例:**

- new-<framework>-workflow — サービス／ワークフロー／ハンドラの足場
- new-migration — マイグレーションテンプレートと gotchas
- create-app — 認証・ログ・デプロイ設定済みの新規アプリ

### 6. コード品質・レビュー

組織の品質基準とレビュー支援。決定的スクリプトやツールを含むことも。フックや GitHub Action で自動実行も。

**例:**

- adversarial-review — 新鮮な目のサブエージェントで批評→修正→ニットピックまで反復
- code-style — Claude がデフォルトで苦手なスタイルの強制
- testing-practices — テストの書き方と何をテストするか

### 7. CI/CD・デプロイ

コードの取得・プッシュ・デプロイ。他スキルを参照してデータ収集することも。

**例:**

- babysit-pr — PR 監視→フレーキ CI 再試行→コンフリクト解消→ auto-merge
- deploy-<service> — ビルド→スモーク→段階的トラフィック→回帰時ロールバック
- cherry-pick-prod — 独立 worktree→cherry-pick→PR

### 8. ランブック

症状（Slack スレッド、アラート、エラー署名）から多ツール調査し、構造化レポートを出す。

**例:**

- <service>-debugging — 症状→ツール→クエリパターン
- oncall-runner — アラート取得→定番確認→所見フォーマット
- log-correlator — リクエスト ID から全システムのログ相関

### 9. インフラ運用

ルーチン保守・運用手順。破壊的操作にはガードレールが効く。

**例:**

- <resource>-orphans — 孤立リソース検出→Slack→ソーク期間→確認後クリーンアップ
- dependency-management — 依存承認ワークフロー
- cost-investigation — ストレージ／エグレス急増の調査パターン

## スキルを作るときの Tips

スキルを作ると決めたら、どう書くか。ベストプラクティス・コツです。

[Skill Creator](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills) も最近リリースしました。

### 当たり前を書かない

Claude Code はコードベースを、Claude はコーディング全般をかなり知っています。主に知識のスキルなら、**通常の思考から外れる情報**に集中してください。

[frontend design skill](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md) は良い例——Inter フォントや紫グラデーションなど典型パターンを避ける味付けを、顧客と反復して作りました。

### Gotchas セクションを作る

スキルで最もシグナルの高いのは **Gotchas** です。Claude がスキル利用でよく踏む失敗から蓄積し、エッジケースに出るたび更新してください。

### ファイルシステムと Progressive Disclosure

スキルは markdown 1ファイルではなく**フォルダ**です。ファイルシステム全体をコンテキストエンジニアリングと progressive disclosure と考えてください。スキル内のファイルを伝え、適切なタイミングで読ませます。

最小形は他 markdown への参照（例: `references/api.md`）。出力が markdown なら `assets/` にテンプレートを置くことも。

references、scripts、examples などのフォルダで効率が上がります。

### Claude をレールに乗せすぎない

Claude は指示に忠実に従いがちです。スキルは再利用されるため、指示が細かすぎると状況に合わせられません。必要な情報を渡しつつ、柔軟性も残してください。

### セットアップを考える

ユーザーコンテキストが必要なスキルもあります。例: スタンドアップを Slack に投稿するスキルはチャンネルを聞く必要があるかもしれません。

スキルディレクトリの `config.json` にセットアップ情報を保存するパターンが有効です。未設定ならユーザーに聞きます。

構造化された複数選択質問には AskUserQuestion ツールを使うよう指示できます。

### description フィールドはモデル向け

セッション開始時、Claude Code は全スキルの description 一覧を構築します。これをスキャンして「このリクエスト用のスキルはあるか」を判断します。description は要約ではなく**トリガー条件の説明**です。

### メモリとデータ保存

スキル内にデータを保存する形のメモリも可能です。追記ログ、JSON、SQLite など。

例: standup-post が `standups.log` に過去投稿を残し、次回は履歴を読んで昨日からの差分を述べる。

スキルディレクトリのデータはアップグレード時に消えることがあるため、安定フォルダ（現状 `${CLAUDE_PLUGIN_DATA}` など）に置くべきです。

### スクリプトを置き、コードを生成させる

Claude に与えられる最強のツールのひとつはコードです。スクリプトとライブラリがあれば、ターンはボイラープレート再構築ではなく**合成**——次に何をするかの判断に使えます。

データサイエンススキルでイベントソースから取得する関数ライブラリを渡し、複雑な分析用にスクリプトをその場で生成させる、といった使い方です。

### オンデマンドフック

スキルは呼ばれたときだけ有効なフックを含められます。常時は嫌だが特定時に極めて有用な、より強い意見のフック向けです。

**例:**

- /**careful** — prod 触り時だけ rm -rf 等を PreToolUse でブロック
- /**freeze** — 特定ディレクトリ外の Edit/Write をブロック（デバッグ時に無関係修正を防ぐ）

## スキルの配布

スキルの大きな利点はチームと共有できることです。

共有の二通り:

- リポジトリにコミット（`./.claude/skills`）
- **プラグイン**と Claude Code プラグインマーケットプレイス（[ドキュメント](https://code.claude.com/docs/en/plugin-marketplaces)）

少数リポジトリの小チームならリポジトリ内で十分です。チェックインするスキルはモデルコンテキストを少しずつ増やします。スケールすると内部マーケットプレイスで配布し、インストールを選ばせる方がよいです。

### マーケットプレイスの運用

どのスキルを載せるか。中央チームが決めるのではなく、**有用なスキルを有機的に見つける**方針です。試してほしいスキルは GitHub のサンドボックスフォルダに上げ、Slack 等で案内します。

十分な traction があれば（オーナー判断）、マーケットプレイスへの PR を出します。

悪い・冗長なスキルは作りやすいので、リリース前のキュレーションが重要です。

### スキルの合成

スキル同士の依存もあります。ファイルアップロードスキルと CSV 生成・アップロードスキルなど。マーケットプレイスにネイティブな依存管理はまだありませんが、他スキル名を参照すれば、インストールされていればモデルが呼び出します。

### スキルの計測

社内では PreToolUse フックでスキル利用をログし（[例](https://gist.github.com/ThariqS/24defad423d701746e23dc19aace4de5)）、人気や期待より undertrigger なスキルを把握します。

## 結論

スキルは強力で柔軟なエージェント向けツールですが、まだ初期で、最適な使い方は皆で模索中です。

これは決定的ガイドというより、うまくいった Tips の詰め合わせです。理解する最良の方法は、作って実験し、自分に合うものを見つけること。多くは数行と1つの gotcha から始まり、Claude が新しいエッジに当たるたびに育てられました。

役に立てば幸いです。質問があれば知らせてください。
