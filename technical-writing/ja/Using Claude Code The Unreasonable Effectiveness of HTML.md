# Using Claude Code: HTML の驚くべき効果

> 原文: [[Using Claude Code The Unreasonable Effectiveness of HTML]]  
> 本記事は [Claude Blog](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html) にも掲載されています。

エージェントが私たちとやり取りする際の主要なファイル形式として、Markdown が支配的になっています。シンプルで移植性が高く、ある程度のリッチテキスト表現ができ、編集も容易です。Claude は Markdown 内に ASCII で図を描くことまで驚くほど上手くなりました。

しかしエージェントがどんどん強力になるにつれ、Markdown は制約の強い形式になってきたと感じています。100行を超える Markdown ファイルは読むのがつらい。もっとリッチな可視化、色、図が欲しい。そして簡単に共有したい。

さらに、これらのファイルを自分で編集することはますます少なくなり、仕様書・参照資料・ブレストの成果物として使うことが多い。編集するときも、たいていは Claude に編集させる——Markdown の最大の利点のひとつが薄れている。

そのため、出力形式として Markdown の代わりに HTML を好むようになり、Claude Code チーム内でも使われ始めている。理由は次のとおり。

（例から始めたい場合は [https://thariqs.github.io/html-effectiveness](https://thariqs.github.io/html-effectiveness) を参照。理由の説明はぜひ読み返してほしい）

## なぜ HTML か

### 情報密度

HTML は Markdown と比べてはるかに豊かな情報を伝えられます。見出しや書式といった単純な文書構造はもちろん、次のような表現も可能です。

- テーブルによる表形式データ
- CSS によるデザインデータ
- SVG によるイラスト
- script タグによるコードスニペット
- JavaScript + CSS によるインタラクション
- SVG と HTML によるワークフロー
- 絶対配置や canvas による空間データ
- image タグによる画像

Claude が読める情報のセットは、ほぼ HTML で十分効率よく表現できると言ってよいでしょう。モデルが深い情報を伝え、あなたがレビューするための非常に効率的な手段になります。

この能力がないと、Markdown では ASCII 図のような非効率な手段に頼ったり——お気に入りは、Claude Code が Unicode 文字で色を推定して見せるスクリーンショットです。

### 視覚的な明瞭さと読みやすさ

Claude がより複雑な仕事をするようになると、仕様やプランもどんどん大きくなります。実際には 100行超の Markdown ファイルは読まないし、組織の他の人にも読んでもらえません。

一方 HTML 文書は読みやすく、Claude がタブ・図・リンクなどで視覚的に最適な構造に整理できます。モバイル対応にして、デバイスに応じた読み方もできます。

### 共有のしやすさ

Markdown は多くのブラウザがネイティブにうまく描画しないため、共有が難しい。メールやメッセージに添付することが多い。

HTML ならファイルをアップロード（例: S3）すればリンクを共有できる。同僚は好きな場所で開き、参照しやすい。

仕様・レポート・PR 説明が HTML なら、実際に読まれる確率ははるかに高くなります。

### 双方向のインタラクション

HTML ではスライダーやノブでデザインを調整したり、アルゴリズムのオプションをいじって結果を見たりできます。うまくいった設定をプロンプトとしてコピーし、Claude Code に貼り戻すことも可能。双方向インタラクションの例は Playgrounds の記事を参照: [https://x.com/trq212/status/2017024445244924382](https://x.com/trq212/status/2017024445244924382)

### データの取り込み

なぜ ClaudeAI や Claude Design ではなく Claude Code で HTML を作るのか。最大の理由のひとつは、Claude Code が取り込めるコンテキストの量です。例えばこの記事を書くとき、コードフォルダ内の HTML ファイルをすべて読み、種類ごとに分類・カテゴリ化し、各タイプを図で表した HTML を作らせました。この記事の図はその結果です。

ファイルシステムのほか、MCP（Slack、Linear など）、ブラウザ（Claude in Chrome）、git 履歴などから追加コンテキストを得られます。

### 楽しい

Claude で HTML 文書を作るのは単に楽しく、制作への関与と没入感が増します——それだけでも十分な理由です。

### はじめ方

この記事を読んで `/html` スキル化する人が出るのが少し心配です。価値はあるかもしれませんが、大げさにしなくてよいと強調したい。Claude に「HTML ファイルを作って」「HTML artifact を作って」と頼むだけで十分です。

コツは、artifact に何をさせたいか、どう使うかを知っていること。スキルは慣れてからでよく、まずはプロンプトから試してユースケースを掴むのがおすすめです。

## ユースケース

具体例として、さまざまな HTML を作ってきました。一覧: [https://thariqs.github.io/html-effectiveness](https://thariqs.github.io/html-effectiveness) 。概要は以下。

### 仕様・計画・探索

HTML は問題に深く入るためのリッチなキャンバスです。問題に取りかかるとき、単純な Markdown プランではなく HTML ファイルのウェブを想定します。ブレストして選択肢を探索させ、ひとつを深掘りし、モックやコードスニペットを足す。納得したら実装プランを書き、新しいセッションですべてのファイルを渡して実装させます。

検証時も検証エージェントにファイルを読ませ、必要なコンテキストを広く持たせます。

**プロンプト例:**

- オンボーディング画面の方向性が決まらない。レイアウト・トーン・密度がはっきり異なる6案を生成し、1つの HTML でグリッド比較できるようにして。各案にトレードオフをラベル付けして。
- 読みやすい実装プランを HTML で作成。モック、データフロー、レビューしたい重要スニペットを含めて。

**向いている用途:**

- コードの別実装の探索
- 複数のビジュアルデザインの探索

### コードレビューと理解

Markdown ではコードが読みにくい。HTML なら diff、注釈、フローチャート、モジュール図などを描画できる。エージェントが書いたコードの理解、レビュー、PR の説明に使えます。GitHub の diff よりうまくいくことが多く、PR には HTML のコード説明を添付するようになりました。

**プロンプト例:**

> この PR を HTML artifact で説明してレビューを手伝って。ストリーミング／バックプレッシャー周りに詳しくないのでそこに焦点を当てて。実際の diff をインライン注釈付きで、重要度で色分けして。

**向いている用途:**

- PR 作成
- PR レビュー
- コード内のトピック理解

### デザインとプロトタイプ

Claude Design は HTML ベースです。最終成果物が HTML でなくても、デザイン表現力は HTML が非常に高い。HTML でスケッチしてから React や Swift など好みの言語に書き換えられます。アニメーションや操作のプロトタイプ、スライダーやノブでの調整も可能です。

**プロンプト例:**

> 新しいチェックアウトボタンのプロトタイプを作りたい。クリックで再生アニメーション、その後すぐ紫に変わる。アニメーションを試せるスライダーとオプションを HTML に。うまくいったパラメータをコピーするボタンも。

**向いている用途:**

- デザインシステム artifact
- コンポーネント調整
- コンポーネントライブラリの可視化
- 楽しいアニメーションのプロトタイプ

### レポート・調査・学習

Claude Code は複数データソースを横断して合成し、読みやすいレポートにするのが得意です。Slack、コードベース、git、Web などを検索させ、自分用・リーダー用・チーム用のレポートを作れます。長い HTML、インタラクティブな説明、スライド形式も可能。SVG で図を足すよう頼むとよいです。プロンプトキャッシュの記事用に、git 履歴を読んだうえで HTML の調査ファイルを作らせたこともあります。

**プロンプト例:**

> レートリミッタの動きがわからない。関連コードを読んで1ページの HTML 説明を: トークンバケットのフロー図、注釈付き主要スニペット3〜4個、末尾に gotchas セクション。一度読む人向けに最適化して。

**向いている用途:**

- 機能の仕組みの要約
- 概念の説明
- 上司向け週次ステータス
- インシデントレポート
- SVG 図・フローチャート・技術図

## カスタム編集インターフェース

テキストボックスだけでは欲しいものを説明しにくいとき、作業中のデータ用の捨てエディタを HTML で1ファイル作らせます。製品でも再利用ツールでもなく、そのデータ専用です。

必ず最後はエクスポート: UI で行った操作を JSON やプロンプトとしてコピーし、Claude Code に貼れるボタンです。

**プロンプト例:**

- Linear チケット30件の優先度付け。各チケットをドラッグ可能なカードにし、Now / Next / Later / Cut の列に。最善の推測で事前ソート。「markdown としてコピー」でバケットごとの順序と1行 rationale。
- フィーチャーフラグ設定のフォームエディタ。エリア別グループ、依存関係、前提フラグがオフのときに警告。変更キーだけの「diff コピー」ボタン。
- システムプロンプト調整。左に編集可能プロンプト（変数スロット強調）、右に3つのサンプル入力でテンプレートをライブ再描画。文字数／トークンカウンタとコピーボタン。

**向いている用途:**

- チケット・テストケース・フィードバックの並べ替え・分類
- 構造化設定（フラグ、env、制約付き JSON/YAML）
- ライブプレビュー付きプロンプト・テンプレート調整
- データセットの承認／タグ付けとエクスポート
- 文書・トランスクリプト・diff への注釈とエクスポート
- 色・イージング・クロップ・cron・正規表現などテキストで書きにくい値の選択

## よくある質問

HTML に切り替えた話をすると、繰り返し聞かれる質問があります。

**トークン効率は悪くない？** Markdown の方がトークンは少ないことが多いですが、HTML の表現力と実際に読む確率の高さから、総合的なアウトプットは良くなっています。Opus 4.7 の 1M コンテキストでは、増加はほとんど気になりません。

**今でも Markdown を使う場面は？** 正直ほぼすべて HTML ですが、HTML 最大主義の極端な側だと思います。

**HTML の見方は？** ローカルでブラウザを開く（Claude に開かせてもよい）、共有可能なリンクが欲しければ S3 などにアップロード。

**Markdown より生成に時間がかかるのでは？** かかります。2〜4倍程度ですが、結果はそれに見合うと感じています。

**バージョン管理は？** HTML の diff はノイズが多く、Markdown よりレビューしにくい——最大のデメリットのひとつです。

**好みのテイストに合わせるには？** frontend design プラグインが有効。社内スタイルはコードベースからデザインシステム HTML を1つ作り、他の HTML の参照に使えます。

## 最新情報を追う

HTML を使う本当の理由は、Claude とのループにいる感覚が強いからだと思います。プランを深く読まなくなり、Claude の選択に任せざるを得なくなるのではないかと不安になっていました。

HTML では、むしろこれまで以上にループにいる感覚があります。あなたもそう感じられることを願っています。
