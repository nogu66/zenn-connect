# Claude Code 構築の教訓: プロンプトキャッシュがすべて

> 原文: [[Lessons from Building Claude Code Prompt Caching Is Everything]]

エンジニアリングでは「Cache Rules Everything Around Me」と言われることが多く、エージェントでも同じです。

Claude Code のような長時間のエージェント製品は、**プロンプトキャッシュ**によって実現可能になります。前のラウンドトリップの計算を再利用し、レイテンシとコストを大きく下げます。

プロンプトキャッシュとは何か、どう動くか、技術的にどう実装するかは [@RLanceMartin の記事](https://x.com/RLanceMartin/status/2024573404888911886) と新しい auto-caching の発表を参照してください。

Claude Code ではハーネス全体をプロンプトキャッシュ中心に構築しています。キャッシュヒット率が高いとコストが下がり、サブスクリプションのレート制限をより寛大にできます。そのためキャッシュヒット率にアラートを張り、低すぎれば SEV を宣言します。

スケールで最適化して学んだ（しばしば直感に反する）教訓です。

## キャッシュのためにプロンプトを並べる

プロンプトキャッシュは**プレフィックス一致**で動きます。API はリクエスト先頭から各 `cache_control` ブレークポイントまでをキャッシュします。並べ順が極めて重要で、できるだけ多くのリクエストがプレフィックスを共有するようにします。

**静的コンテンツを先、動的コンテンツを後**にするのが最善です。Claude Code では次のようになります。

1. **静的システムプロンプト**とツール（グローバルキャッシュ）
2. **Claude.MD**（プロジェクト内キャッシュ）
3. **セッションコンテキスト**（セッション内キャッシュ）
4. **会話メッセージ**

これでセッション間のキャッシュヒットを最大化します。

しかし驚くほど壊れやすいです。過去に順序を壊した例: 静的システムプロンプトに詳細なタイムスタンプを入れた、ツール定義の順序を非決定的にシャッフルした、ツールパラメータを更新した（例: AgentTool が呼べるエージェント）など。

## 更新はメッセージで渡す

プロンプト内の情報が古くなることがあります（時刻、ユーザーがファイルを変更したなど）。プロンプトを更新したくなるかもしれませんが、キャッシュミスになりユーザーに高コストになることがあります。

次のターンでメッセージ経由で渡せないか検討してください。Claude Code では次のユーザーメッセージやツール結果に `<system-reminder>` で更新情報を入れ、キャッシュを保ちます（例: 今日は水曜日）。

## セッション途中でモデルを変えない

プロンプトキャッシュはモデルごとに別物で、直感に反するコスト計算になります。

Opus で10万トークン会話したあと、簡単な質問を Haiku に切り替えると、Haiku 用にキャッシュを再構築する必要があり、Opus のまま答えるより高くなることがあります。

モデル切り替えが必要なら、サブエージェントがよく、Opus が別モデルへの「引き継ぎ」メッセージを準備します。Claude Code の Explore エージェント（Haiku）でよく行います。

## セッション途中でツールを増減しない

会話の途中でツールセットを変えるのは、キャッシュを壊す最も一般的な方法のひとつです。「今必要なツールだけ」は直感的ですが、ツールはキャッシュされたプレフィックスの一部なので、1つ足す／減らすだけで会話全体のキャッシュが無効になります。

### Plan Mode — キャッシュ制約に合わせた設計

Plan mode は良い例です。直感的には plan mode 入り時に読み取り専用ツールだけに差し替えたくなりますが、それはキャッシュを壊します。

代わりに、**常に全ツールをリクエストに含め**、EnterPlanMode / ExitPlanMode をツール自体にします。plan mode オン時は、plan mode であることと指示（コードベース探索、ファイル編集しない、完了時に ExitPlanMode）をシステムメッセージで伝えます。ツール定義は変わりません。

副次効果: EnterPlanMode をモデル自身が呼べるため、難しい問題を検知したら自律的に plan mode に入れ、キャッシュを壊しません。

### Tool Search — 削除ではなく defer

同じ原則が tool search にも当てはまります。数十の MCP ツールを毎リクエスト全部載せるのは高コストですが、途中で削除するとキャッシュが壊れます。

解: **defer_loading**。削除せず、ツール名だけの軽量スタブ（`defer_loading: true`）を送り、必要なら ToolSearch で「発見」させます。完全なスキーマは選択時だけ読み込みます。キャッシュされたプレフィックスは安定——同じスタブが常に同じ順序で存在します。

API の [tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool) で簡略化できます。

## コンテキストのフォーク — コンパクション

コンテキストウィンドウが尽きるとコンパクションが起きます。これまでの会話を要約し、その要約で新セッションを続けます。

コンパクションはプロンプトキャッシュと組み合わせると、直感に反するエッジが多いです。

コンパクト時は要約のため会話全体をモデルに送る必要があります。別 API 呼び出しで別システムプロンプト・ツールなし（単純実装）だと、メイン会話のキャッシュプレフィックスと一致せず、入力トークン全額を払い、ユーザーコストが急増します。

### 解 — キャッシュセーフなフォーク

コンパクション時は、親会話と**同じ**システムプロンプト・ユーザーコンテキスト・システムコンテキスト・ツール定義を使います。親の会話メッセージを前置し、末尾にコンパクションプロンプトを新しいユーザーメッセージとして追加します。

API から見ると親の最後のリクエストとほぼ同じ——同じプレフィックス・ツール・履歴——なのでキャッシュプレフィックスが再利用されます。新トークンはコンパクションプロンプトと要約出力だけです。

そのため**コンパクション用バッファ**を確保し、コンパクトメッセージと要約出力用の余裕を残します。

Claude Code の学びを [compaction API](https://platform.claude.com/docs/en/build-with-claude/compaction#prompt-caching) に反映しているので、自アプリでも同パターンを適用できます。

## 学んだこと

1. **プロンプトキャッシュはプレフィックス一致。** プレフィックスのどこかが変わると以降すべて無効。システム全体をこの制約で設計し、順序を正せば多くは無料でキャッシュされる。
2. **システムプロンプト変更よりメッセージ。** plan mode 入り、日付変更などをシステムプロンプト編集でやりたくなっても、会話中のメッセージ挿入の方がよい。
3. **会話途中でツールやモデルを変えない。** 状態遷移はツールでモデル化（plan mode）。ツール読み込みは削除ではなく defer。
4. **キャッシュヒット率を可用性のように監視。** キャッシュ破壊にアラートし、インシデント扱い。数ポイントのミス率でもコストとレイテンシに大きく効く。
5. **フォーク操作は親と同じプレフィックスを共有。** コンパクション・要約・スキル実行などは、同一のキャッシュセーフパラメータで親プレフィックスにヒットさせる。

Claude Code は初日からプロンプトキャッシュ中心です。エージェントを作るなら同様にすべきです。
