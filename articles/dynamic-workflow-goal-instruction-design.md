本記事では、**Dynamic workflow** と **`/goal` コマンド**を焦点に当て、使用する上での課題と問題点を挙げるともに、その解消方法についても併せて紹介いたします。

前編を読むと、Dynamic workflow と `/goal` を組み合わせれば、手動チューニングに頼らずスキルを育てられることがわかります。

しかし実際に試すと、次の壁にぶつかります。

- Dynamic workflow に「検証して」とだけ言うと、何をどこまでやるかが曖昧になる
- `/goal` に「改善して」とだけ言うと、いつ終わりか判断できない

**本質は、2つの指示が明確であるほどループの精度が上がる**という点にあります。

| 仕組み | あなたが決めること |
| --- | --- |
| **Dynamic workflow** | どういう風な作業を実行するか |
| **`/goal` コマンド** | 実行を続ける条件はなにか |

本記事では、この2つを分けて、**渡すべき指示の設計方法**を整理します。

**この記事の対象読者**
- 前編のワークフローを試したが、指示の書き方で迷っている方
- Dynamic workflow や `/goal` の効果が安定しないと感じている方

**この記事でわかること**
- Dynamic workflow に渡す「作業内容」の書き方
- `/goal` に渡す「完了条件」の書き方
- 2つを組み合わせた指示テンプレート

**この記事で扱わないこと**
- Dynamic workflow / `/goal` の基本概念（前編を参照）
- Skills の作成手順そのもの

## Dynamic workflow に渡す指示：どういう風な作業を実行するか

Dynamic workflow は、サブエージェントを並列・直列に動かして大きな作業を進める仕組みです。
ここで渡す指示は、**「何を」「どの観点で」「どんな成果物まで」** をはっきりさせるものです。

### 指示に含めるべき4要素

<!-- TODO: 各要素を具体例付きで展開 -->

1. **対象（Scope）** — どのファイル・スキル・リポジトリを見るか
2. **観点（Dimensions）** — 何の観点で調査・検証するか（例: 正確性 / 一貫性 / 網羅性）
3. **プロセス（Process）** — 並列調査 → 再検証 → 統合、など実行の型
4. **成果物（Output）** — レポート形式、優先度付きの指摘リスト、など

### 悪い例と良い例

**悪い例** — 作業内容が特定できない

```bash
ultracode でこのリポジトリ内のスキルを検証してください。
```

**良い例** — 作業の型と観点が読み取れる

```bash
ultracode で open-computer-use スキルを検証してください。

- Find: スキル作法 / CLI記述の正確性 / MCP・インストール記述 / ファイル間一貫性 の4観点を並列調査
- Verify: 各指摘を実ファイルで再確認し、誤読を棄却
- Synthesize: 確認済みの指摘のみで日本語レポートを生成（重大度付き）
```

### Dynamic workflow 用プロンプトテンプレート

```bash

- Find: [観点1] / [観点2] / [観点3] を並列調査
- Verify: [再検証のルール]
- Synthesize: [成果物の形式と言語]
```

## `/goal` に渡す指示：実行を続ける条件はなにか

`/goal` は、**完了条件が満たされるまで** エージェントが自律的にターンを重ねる仕組みです。
ここで渡す指示は、**「いつ止めてよいか」** を機械的に判定できる形に落とすものです。

### 完了条件に含めるべき3要素

<!-- TODO: 各要素を具体例付きで展開 -->

1. **検証可能（Verifiable）** — ファイルの存在、テスト結果、チェックリストなど、Yes/No で判定できる
2. **客観的（Objective）** — 「良い感じ」ではなく、第三者が同じ結論に至れる
3. **スコープ限定（Scoped）** — 前段の Dynamic workflow の指摘に対応している（無限に改善し続けない）

### 悪い例と良い例

**悪い例** — 終了条件が曖昧

```bash
/goal 指摘された問題点を改善して欲しいです。
```

**良い例** — 何が満たされれば終わりかが明確

```bash
/goal 前回の検証レポートの Critical / High 指摘をすべて解消してください。

完了条件:
- 各指摘項目に対応する修正が SKILL.md または関連ファイルに反映されている
- Verify エージェントが再実行され、同じ指摘が再検出されない
- CLI 操作例に --bundle-id など、他行と整合する必須オプションが明記されている
```

### `/goal` 用プロンプトテンプレート

<!-- TODO: コピペ用テンプレートを整備 -->

```bash
/goal [前段の成果物] に基づき [やること] してください。

完了条件:
- [条件1: 検証可能な状態]
- [条件2: 検証可能な状態]
- [条件3: 再検証で指摘が消えること]
```

## 2つを組み合わせると、スキルは“育つ”ループになる

Dynamic workflow と `/goal` は、役割が逆です。

- **Dynamic workflow** → 広く・多角的に**問題を見つける**
- **`/goal`** → 狭く・深く**問題を直し切る**

<!-- TODO: 前編の open-computer-use 事例を、指示の Before/After で再構成 -->

```text
[Dynamic workflow] 多角的検証 → 指摘レポート
        ↓
[/goal] 指摘の解消条件を満たすまで改善ループ
        ↓
（必要なら再度 Dynamic workflow で回帰検証）
```

**指示が曖昧なとき** — 検証も改善も「平均点」で止まりやすい
**2つが明確なとき** — 見つける精度と直し切る確度が両方上がる

## チェックリスト：送る前に確認する

### Dynamic workflow の指示

- [ ] 対象（ファイル・スキル名）が具体的か
- [ ] 調査観点が列挙されているか
- [ ] 成果物の形式（レポート / リスト / 言語）が指定されているか
- [ ] Find → Verify → Synthesize のようなプロセスが読み取れるか

### `/goal` の指示

- [ ] 前段の成果物（レポート等）への参照があるか
- [ ] 完了条件が Yes/No で判定できるか
- [ ] スコープが「今回直す範囲」に限定されているか
- [ ] 再検証で指摘が消える、など終了の客観基準があるか

## おわりに

Dynamic workflow と `/goal` の威力は、機能そのものより **渡す指示の明確さ** に比例します。

- Dynamic workflow には **どういう風な作業を実行するか**
- `/goal` には **実行を続ける条件はなにか**

この2つがはっきりしていれば、前編で紹介したスキル育成ループは、再現性の高い運用に近づきます。
