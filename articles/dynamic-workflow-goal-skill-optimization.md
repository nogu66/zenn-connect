## 実践ワークフロー

<!-- 体験 Attempt 連載 — 手動 → dynamic workflow → /goal -->

### 手動チューニングでは、スキルは“平均点”で止まる

<!-- 試行1 -->

- **What**: 手動でやったこと（プロンプト修正、例の追加、…）
- **Why うまくいかなかったか**
  - 検証軸が頭の中だけ
  - 未達がログに残らない
  - 毎回別の手直し → スキル本体が育たない
- **読者への含意**: 「精度が低い」＝本文の問題と成功条件の未定義が混ざっている

### 多角検証しないと、直すべき場所が言語化されない

<!-- 転換1 — dynamic workflow での検証 -->

- **What**: 成功条件ごとにファンアウトして判定
- **Why 効いたか**: 人間が一度に見落とす観点を並列化できる
- **具体（要記入）**: dynamic workflow で洗い出した未達・問題点 3〜5 個
  - [ ] 未達1:
  - [ ] 未達2:
  - [ ] 未達3:
- **素材**: 採点ログ抜粋 or スクリーンショット
- **How（後半に回す）**: 擬似コード（goal → parallel checks → 差分修正ループ）

### /goal を止め条件にすると、手動より初期精度が上がる

<!-- 転換2 — /goal で改善が終わるまで -->

- **Why**: 「だいたい良さそう」で終わらせない／未達だけ直す
- **手動 vs /goal 対比表**（要数値があれば1行）
  - 終了条件 / 修正単位 / スキルへの還元
- **実際に使った `/goal` 全文**（要貼り付け）
- **収束**: ラウンド数・トークン感（任意）

## 2つを組み合わせると、スキルは“育つ”ループになる

<!-- 一般化 — 概念セクションの実践への落とし込み -->

```
/goal（検証可能な成功条件）
  → dynamic workflow（分岐・ファンアウト・差分修正）
  → 実行結果
  → ゴールで採点
  → スキルへ還元
  ↺ ループ
```

- **要点**: ゴールは実行の入力かつ評価基準（同じ `/goal` で導く＋採点する）

### /goal を“検証可能”に書く

- 悪い例 / 良い例（コピペ用テンプレ）
- Why: 採点可能 → 最適化の方向が一意

### dynamic workflow でゴールに従わせる

- ファンアウト / 早期終了 / 差分修正の3点だけ

### 採点結果をスキルに還元する

- 繰り返し未達 → 手順への昇格（diff 例）
