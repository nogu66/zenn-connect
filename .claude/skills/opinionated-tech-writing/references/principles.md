# 7原則の詳細解説

このファイルは `SKILL.md` で要約した7原則の、より深い解説と実例集です。
記事を書く際に「具体的にどう書けばいいか」迷ったとき、ここを参照します。

---

## 原則1: Hill I will die on（譲れない原則）から始める

### なぜ重要か

冒頭3秒で「これは私のための記事だ」と思わせなければ、読者はもう戻ってこない。
中立紹介はSEO以外では誰の記憶にも残らない。

### 形式

- **タイトル**: 主張を含む（疑問形・断定形のどちらかが強い）
- **冒頭1文**: 個人の確信を表明する

### 悪い例 vs 良い例

| ❌ 弱い | ✅ 強い |
|--------|--------|
| 「Claude Skillsについて解説します」 | 「Skillsを使い始めて1ヶ月、もうSystemプロンプトに戻れない」 |
| 「File Systemの活用方法を紹介」 | 「Agentの状態管理は全部File Systemに寄せろ」 |
| 「Bashツールも便利です」 | 「非コーディングのAgentでもBashだけで十分」 |
| 「Prompt Cachingのメリット」 | 「Cachingを設定してないAgentはお金を捨てている」 |

### Thariq氏の実例

- 「Your Agent should use a File System」
- 「Why even non-coding agents need bash」
- 「my favorite way to use Claude Code to build large features is spec based」

すべて**断定形**で**個人視点**。これがHillの形。

### 注意点

- 「死ぬほど信じてないこと」は書かない（嘘くさくなる）
- 過剰な煽り（「絶対◯◯すべき！」連呼）は逆効果。確信は静かに書く方が伝わる

## 原則2: Whyを徹底的に深掘りする

### なぜ重要か

How だけの記事は **Stack Overflow で代替可能**。
Why が刺さる記事は **保存され、共有され、引用される**。

### Whyを深める3つの素材

1. **失敗談**: 「以前は◯◯でハマっていた」
2. **比較**: 「△△と比べて、〇〇はここが優れている」
3. **数値・具体結果**: 「コンテキスト使用量が40%減った」「Issue対応時間が半分になった」

### 悪い例 vs 良い例

❌ Why が薄い：
> File Systemを使うとAgentが安定します。状態を永続化できるので便利です。

✅ Why が深い：
> 以前は会話履歴を全部Systemプロンプトに詰め込んでいた。これだと10ターン超えたあたりでAgentが「最初の指示」を忘れ始める。grepで複数箇所を再検証するクセもなくなり、幻覚が増えた。File Systemに状態を吐き出すようにしたら、context_used が平均40%下がり、ハルシネーション率も体感で半減した。

違いは **「自分の失敗」「比較」「数値」が全部入っているか**。

### Why を書くときの自問

- 「私はなぜこれを推すのか？最初に試したきっかけは？」
- 「これを試す前、何で困っていたか？」
- 「他に検討した選択肢は何で、なぜ捨てたか？」
- 「導入後、何が変わったか？数値で言えるか？」

これに答えていけば自然と Why が深まる。

## 原則3: 自分の実例から書く

### なぜ重要か

抽象論は誰でも書ける。**「私の◯◯では実際にこうやった」**は、その人にしか書けない。
読者は「この人は実際に作ってる人だ」と直感的に判断する。

### 実例の入れ方

- スクリーンショット（実行結果、ダッシュボード、エラー画面）
- コードのコピー（伏字でいい部分は伏せて、全体構造を見せる）
- ログ・出力の抜粋
- 自分のリポジトリへのリンク

### Thariq氏の例

- Email Agent でのファイル操作の実装画面
- 自分のSlack向けAgentがbashでffmpegを叩く様子
- Claude Code の実セッションのスクリーンショット

### 「実例がまだ無い」とき

正直に書く方が信頼される：

> 「正直まだ本番投入はしていない。社内ツールで2週間試した範囲では、◯◯という効果が出ている」

これは隠して書くより遥かに刺さる。

### ❌ 避けるべき「実例風の架空」

> 「ある企業ではこの手法でROIを3倍にしました」（出典なし）

→ 信頼を即失う。**自分の手で触っていないものは書かない**。

## 原則4: 1セクション1アイデアの構造

### なぜ重要か

技術記事は **流し読みされる前提** で書く。1セクションに2つ以上の主張があると、片方が必ず埋もれる。

### 構造化のテクニック

- **小見出しを多用** — 5行に1つ目安
- **箇条書き・番号** — 並列の概念は箇条書き、順序のあるものは番号
- **太字** — 1段落に1〜2個まで（多すぎると逆に読みにくい）
- **画像・図** — 言葉で500字説明するより1枚の図

### 用途別ラベリングのパターン

Thariq氏のBashスレッドの構造：
1. Chaining API Calls
2. Video & File Editing
3. Reoccurring Tasks
4. ...

各セクションが **「Bashが効く具体的な場面」** という単一アイデア。これを並べることで全体の主張（Bashだけで十分）が成立する。

### 悪い構造 vs 良い構造

❌ 「Bashの使い方とFile Systemとの連携、Cachingのコツ」（複数主張が混在）
✅ 「## Bashで何ができるか」「## File Systemとの組み合わせ」「## Cachingの注意点」（章で分離）

## 原則5: 読者の Next Step を明示する

### なぜ重要か

良い記事は読者を **「動かす」**。読み終わって「ふーん」で終わる記事は価値が半減する。

### Next Step の3レベル

1. **最小行動**: 「このコマンドを今すぐ叩いてみてください」
2. **試行**: 「このリポジトリをcloneして、◯◯を変えるとどうなるか試してください」
3. **発展**: 「次のステップとして◯◯と組み合わせると、さらに効果が上がります」

### Thariq氏の例

- 「Claude Agent SDKでこう実装できる（リンク）」
- 「sandboxで権限設定をしておくと安全」
- 「自分の現在のセッションでこれを試してみて」

### 悪い例 vs 良い例

❌ 「いかがでしたでしょうか。ぜひ試してみてください」（行動が曖昧）
✅ 「まずは `npx zenn preview` でローカル起動して、自分の最近の記事に上の主張型タイトルを付け直してみてください。10分でできます」

## 原則6: 人間味と専門性の両立

### なぜ重要か

専門性だけ → 退屈な技術ドキュメント
人間味だけ → 中身のないポエム

両方あって初めて「この人の記事は読みたい」になる。

### 人間味を出す表現

- 「正直、最初は半信半疑だった」
- 「このツールには本当に救われた」
- 「2日連続で徹夜してハマった話」
- 「I put a lot of heart into this」（Thariq氏の常套句）

### でも内容は妥協しない

人間味で「技術の浅さ」をごまかさない。
むしろ感情を表に出す代わりに、**技術詳細はより深く、より具体的に書く**。

### バランスの取り方

- 段落の頭は人間味（フック）
- 段落の中身は専門性（実装、数値、コード）
- 段落の終わりは Next Step（行動）

例：
> 正直、最初はFile Systemをわざわざ使う意味が分からなかった。が、Email Agentで会話が10往復を超えたあたりでcontext使用量が25k → 8kに激減した瞬間に、考えが180度変わった。具体的には、`/sessions/<id>/messages/` 以下にメッセージを順次書き込み、必要な時だけgrepで取り出す構造だ。今すぐ試したいなら、Claude Agent SDKの `bash` ツールを有効にして `mkdir -p sessions/test` から始めてみてほしい。

## 原則7: メタ技法も惜しまず公開する

### なぜ重要か

読者は **「How」より「How to find Hows」** を求めている。
技術トピックそのものより、「あなたが普段どうやって学んでるか・書いてるか・作ってるか」のメタ情報の方が、しばしば価値が高い。

### Thariq氏のメタ技法例

- **Specベース執筆**: 記事を書く前に、AskUserQuestionToolで自分に40問インタビューしてSpec化
- **新セッション原則**: Specができたら、コンテキストの汚れていない別セッションで本文を書く
- **Playgrounds活用**: ビジュアル迭代で複数案を並べて比較

これらは記事の本題ではないが、**読者の執筆フロー全体に影響する**。

### あなたのメタ技法を出す

- 普段使っているツールの組み合わせ
- 失敗を防ぐためのチェックリスト
- 自分なりのデバッグ手順

これを記事の最後や別記事で出すと、読者の信頼が一気に上がる。

- [ ] **原則1**: 冒頭1文は個人の確信を表明しているか？
- [ ] **原則2**: 失敗・比較・数値のいずれかが入っているか？
- [ ] **原則3**: 自分が触った実例（or 「試している最中」の正直な記述）があるか？
- [ ] **原則4**: 1セクション1アイデアになっているか？小見出し5行に1つ目安か？
- [ ] **原則5**: 末尾に具体的な Next Step があるか？
- [ ] **原則6**: 人間味と専門性が両立しているか？どちらかに偏ってないか？
- [ ] **原則7**: メタ技法（自分の作り方・調べ方）を1つは出しているか？

7つ全て満たさなくてもいい。**5つ以上なら出して大丈夫**。
