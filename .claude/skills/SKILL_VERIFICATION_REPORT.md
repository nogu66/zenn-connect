## スキル改善の推奨アクション

優先度はjudgeのskillLevelSignal（再現性のある構造的問題）を上位に、表記・明示性の改善を下位に置く。

### 優先度 高

1. **opinionated-tech-writing: 壁打ち（ideation）フェーズの手順を明示的なファネルとして規定する**（唯一のFAILの根本原因）
   - id 2のjudge指摘: 複数runで「Specベース執筆の提案」と「20-40項目のリストアップ」が一貫して脱落する可能性。
   - 対応案: SKILL.mdに順序付きステップを明記 — (a) Specベース執筆を推奨手法として提案 → (b) 20-40項目をブレインスト → (c) 主張1行に絞り込み → (d) 初めてアウトライン化。これらを任意の装飾ではなく必須ステップとして扱わせる。

2. **opinionated-tech-writing: 出力テンプレートの「7段構造」表記を実体の節数に統一する**（id 0で毎回誘発しうる軽微な矛盾）
   - 対応案: SKILL.mdのテンプレ見出しを「8段」に統一するか、タイトルをカウント外と明記。「7段」と書いて8節を並べる食い違いを構造的に解消。

### 優先度 中

3. **zenn-article-writer: 承認ゲートのワークフローをSKILL.mdに明記する**（合成eval id 0で検出した設計齟齬）
   - judge指摘: expected_outputは「提案」（構成案提示→承認→本文）を期待するが、SKILL.mdのExample Application/Quality Checklistは完成記事の一括生成を前提に書かれており両者に齟齬。
   - 対応案: いずれかに統一 — 承認ゲートを意図するなら「構成案提示→承認→本文」をSKILL.mdに明記する。一括生成が正なら、評価側のexpected_outputの「提案」表現を見直す。
   - ※合成evalでの検出のため、実プロンプトでの再現確認を先に行うことを推奨。

4. **zenn-article-writer: 明確化質問フェーズで構成と動くコード例の方針を明示的に発話させる**（id 1の2つのpartial）
   - judge指摘: はじめに/本論/おわりに構成と「動く（テスト済み）コード例」の推奨が、ARTICLE_TEMPLATE.mdの暗黙読込に埋もれユーザーに伝わっていない。evalが繰り返し過小評価する原因。
   - 対応案: 明確化ターンで、想定構成と「テスト済みコード例・プロンプト例を含める」コミットメントを一言ユーザーに提示するよう指示。

### 優先度 低（題材適合・明示性の微調整、スキル欠陥ではない）

5. opinionated-tech-writing（id 1）: 失敗談に「具体的なコスト/損失を伴う失敗」を1つ含めるようSKILL.mdが促す。現状は非効率の指摘どまり。
6. tech-article-structure（id 1, 2）: 却下したストーリーパターンの理由を1行で明示する習慣、題材にコピペ用プロンプト要素が薄い場合はその置換を一言断る習慣を促すと満点に近づく。ただしjudgeは3ケースとも「スキル欠陥なし」と評価しており、優先度は最低。

### トリガー（description）

- 修正不要。9/9正解、under/over-triggerともゼロ、descriptionFixの提案もゼロ。3スキルの境界（主張駆動 / 構造設計 / 課題解決ナラティブ）は現状のdescriptionで正しく機能している。
