# ストーリーパターンとセクション内マイクロ構造

## パターン1 — 違和感 → 転換点 → 新常識

読者が当然と思っている前提を揺らし、自分の転換点を見せ、新しい判断基準を渡す。タイプA向き。

| 段階 | 内容 |
|------|------|
| 共有前提 | みんな〇〇している |
| 個人の限界 | 具体的なストレス（数字・場面） |
| 転換 | 前提が変わった理由 |
| 新常識 | 読者が持ち帰る判断基準 |

冒頭例: 「みんな Markdown を使っている。でも私は100行を超えると読まなくなった」

## パターン2 — 決断フレーム

選択肢が複数あるテーマで使う。自然な行動を否定せず、より良い代替を「一つ選ぶなら」で推す。

- 自然な行動（そのまま続ける等）を**認める**
- より良い代替を**「一つ選ぶなら」**で推す
- 各選択肢に**いつ使うか / 失敗例**をセット

「やるべきことリスト」だけにせず、**分岐 + 判断基準**として書く。

## パターン3 — 直感 vs 制約 → 設計

タイプB向き。エンジニアの直感とシステムの制約を対立させ、その下での設計解を導く。

```text
エンジニアの直感: 今必要なツールだけ渡したい
システムの制約:  prefix が変わるとキャッシュ全損
設計の答え:     ツールを減らさず、状態はメッセージで表現
```

読者は実装テクニックより**制約下の設計思考**を持ち帰る。

## パターン4 — Attempt 連載

試行錯誤があったテーマで使う。失敗を隠さないことが信頼の源。

- 失敗を隠さない
- 各 Attempt に**1〜2文の「なぜダメだったか」**
- 最終解の評価に**「モデル／実装が自然に好んで使うか」**まで含める

見出し例: `## 試行1 — ○○をパラメータに足す`

## パターン5 — 比喩で世界観を固定

難しい概念を1つの比喩で掴ませる。**1記事1比喩**。日本語では1段落で完結させる。

| 参考記事 | 比喩 |
|---------|------|
| Seeing like an Agent | 難しい数学問題 × 紙・電卓・PC |
| Session Management | 分岐点 / 未来の自分への handoff |
| Prompt Caching | prefix match = 上から積むスタック |

## セクション内のマイクロ構造

1セクションは次の4要素で組むと、見出しスキャンでも本文精読でも機能する。

1. **主張1文**（見出しと同義の断言）
2. **観察**（チーム・自分の経験）
3. **具体例**（コード・プロンプト・製品の挙動）
4. **読者への含意**（what you should do）

抽象論だけになりそうなときは、**プロンプト1つ + 失敗例1つ**を足すと一気に具体化する。

## 具体性の置き方

- **プロンプトは全文** — そのままコピーできる形で
- **失敗シナリオ** — 「こうすると壊れる」を1つ
- **数字** — 「100行」「300–400k tokens」「3.2倍（手元計測）」
- **製品名・機能名を隠さない** — 「他ツール」ではなく固有名詞で

数字が無いときは捏造せず「体感では明らかに速い」と正直に書く方が信頼される。

## 声のトーン

- **断定と謙虚の併用** — 「極端な側だが」「決定的なガイドではない」を要所に
- **観察ベース** — 「〜と感じた」「〜が多い」（伝聞「〜と言われている」より一人称）
- **反論への先回り** — FAQ / caveat で読者の合理的なツッコミに答える
- **記事間リンク** — 前提記事・関連記事へ繋いでシリーズ感を出す

声・主張をさらに強めたいときは `opinionated-tech-writing` スキルの7原則を併用する。
