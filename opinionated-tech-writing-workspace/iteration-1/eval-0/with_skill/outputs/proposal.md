## 1. タイトル案（3つ／トーン別）

### 強硬（断定・煽り気味）
**「Skillsを使い始めて、もうCLAUDE.mdベタ書きには戻れない」**

- 「もう戻れない」で個人の確信を最初に出す
- 比較対象（CLAUDE.mdベタ書き）を固有名詞で出して具体性を担保
- Thariq氏の「my favorite way is...」「we can't go back to...」型のフォーマット

### 中庸（自然なトーン）
**「Claude Code Skillsは"再現可能なワークフロー"を渡す道具だ」**

- 主張は入れつつ、煽りは抑える
- 「再現可能なワークフロー」というSkillsの本質を1行に圧縮
- ブクマされやすい中立寄りの言い回し

### 謙虚（控えめだが具体的）
**「Skillsを2週間使って分かった、"プロンプト資産"の貯め方」**

- 期間を入れて経験ベースであることを示す
- 「プロンプト資産」という独自フレーミングで興味を引く
- 控えめながら「使い込んだ人だけが書ける」感を出す

> **採用おすすめ:** 強硬案。Skillsは"温度感"が伝わってこそ価値が分かる機能なので、Hillをはっきり立てた方が刺さる。

## 3. 記事構成のドラフト（7段構造）

### ① タイトル
**「Skillsを使い始めて、もうCLAUDE.mdベタ書きには戻れない」**

### ② 冒頭（Hill I will die on）
上記の冒頭1文をそのまま配置。3〜4行で勢いを切らさず本文へ。

### ③ 問題提起 — 「あなたもこんな経験ありませんか？」
- 同じZenn記事執筆プロンプトを3回コピペしている自分に気づく
- CLAUDE.mdが膨らみすぎて、Claudeが「最初の方の指示」を無視し始める
- プロジェクトごとに同じ「コミットメッセージのルール」を貼り直している
- 「あの便利だったプロンプト」がチャット履歴の海に沈んでいる
→ **「これ全部、3週間前の僕です。」**

### ④ Why の深掘り（最重要セクション）
**(a) 過去の失敗談**
- CLAUDE.mdに執筆ルール・コミット規約・MCP設定の使い方を全部詰めた結果、ファイルが800行を超えて、肝心の最新指示が無視されるようになった
- 「Skillsって所詮.mdの集合でしょ」と判断して導入を後回しにしていた

**(b) 他アプローチとの比較**
- カスタムスラッシュコマンド: 起動はできるが「いつ使うか」のトリガー判定がClaude任せにならない
- CLAUDE.mdベタ書き: 全部読み込まれてcontextを食う／起動条件を絞れない
- MCPサーバー: ツール提供は強いが「ワークフロー（手順書）」は別概念
- → Skillsは「description で起動条件を制御 × on-demand読み込み」がハマる

**(c) 数値・体感の差分**
- CLAUDE.md: 800行 → 150行（必要な常時ルールだけ残す）
- "繰り返しプロンプト" のコピペ回数: 週10回 → 0回
- 記事執筆フローの所要時間: 体感で約30%短縮（Specベース執筆が自動化されたため）

### ⑤ How（具体的なやり方）
1. **Skillの最小構成を理解する** — `SKILL.md` + `references/` + `assets/`
2. **description で発火条件を設計する** — 「いつ使うか」をLLMが判定できる粒度で書く
3. **references/ に深掘り情報、assets/ にテンプレートを置く** — SKILL.md本体は薄く保つ
4. **personal vs project を使い分ける** — `~/.claude/skills/` と `.claude/skills/` の境界
5. **既存スキル（zenn-article-writer等）と組み合わせる** — 重複ではなく相補にする

### ⑥ 実例・コード・画像
- 自分のzenn-connectリポジトリの `.claude/skills/opinionated-tech-writing/` を題材に
- SKILL.mdのfrontmatter（特にdescription）の実物を抜粋して載せる
- 「壁打ちフェーズ」で自分が実際にこのSkillを使ってタイトル案を出させているスクリーンショット
- ディレクトリツリー（`SKILL.md / references/ / assets/`）の図

### ⑦ 注意点・落とし穴
- description が曖昧だとSkillが起動しない／逆に過剰起動する
- Skillの中身は読み込まれるまで隠れているので、起動条件設計を間違えると気づきにくい
- references/assets を増やしすぎるとどこに何があるか自分が忘れる
- "Skill化に値しないもの" もある（1回しか使わないプロンプトはSkillにしない方が早い）

### ⑧ Next Step（読者が今すぐ動けるように）
1. **5分で試す:** `~/.claude/skills/my-first/SKILL.md` を作って、description に「Use this skill whenever I ask about X」と書く
2. **30分で試す:** 普段繰り返しコピペしているプロンプトを1つ選び、SKILL.md化してみる
3. **発展:** description チューニングのために、別セッションで「このSkillはいつ起動すべき？」と Claude に逆質問する

## 4. Spec の最初の10項目（伝えたいこと）

> Specベース執筆ワークフロー Step 1-3 に従い、順番は気にせず思いついたものから。

1. CLAUDE.mdに全部詰める運用は、ファイル肥大化で破綻する（自分の800行体験）
2. Skillsの本質は「ファイル群」ではなく「**descriptionによる起動条件制御**」にある
3. SKILL.md本体は薄く保ち、深い情報は references/ に逃す設計が効く
4. assets/ にテンプレート（記事フレーム、Specシートなど）を置くと再現性が跳ね上がる
5. personal Skill（`~/.claude/skills/`）と project Skill（`.claude/skills/`）の使い分けがコツ
6. カスタムスラッシュコマンドとの違いは「起動判定をClaudeに委ねるか、ユーザーが明示するか」
7. MCPは「ツール」、Skillsは「ワークフロー（手順書）」 — レイヤーが違う
8. 良いdescriptionの書き方: 「Use this skill whenever ...」+ 具体トリガー語の列挙
9. Skill化に向くもの: 繰り返し発生する作業／設計判断の伴う手順／チームで共有したいルール
10. Skill化に向かないもの: 1回限りの作業／コンテキストが毎回違いすぎるもの
