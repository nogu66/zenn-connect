## 記事構成案

### ターゲット読者
- Claude Code を日常的に使っているが、`CLAUDE.md` か個別プロンプトで運用している人
- チームでAIワークフローを標準化したいが、共有方法に悩んでいる人
- 「Agent Skills」「Custom Skills」という言葉を聞いたが、何が嬉しいのか腹落ちしていない人

### 想定文字数
6,000〜8,000字（読了 10〜12分）

---

### 1. はじめに — なぜ今 Skills なのか（500字）
- 対象読者の明示
- この記事の範囲：「Skills の基本」「自作手順」「実運用での落とし穴」
- 範囲外：MCP との比較深堀り、Anthropic API の Skill 機能（Claude Code に閉じる）
- 読了後に得られるもの：自作 Skill 1本を動かせるレベル

### 2. 課題：CLAUDE.md と "毎回プロンプト" の限界（800字）
- **痛み1**：CLAUDE.md が肥大化して LLM のコンテキストを圧迫する
- **痛み2**：作業ごとに違うプロンプトを毎回コピペする運用の辛さ
- **痛み3**：チームメンバーに「あのプロンプト送って」と聞かれる属人化問題
- スクリーンショット案：自分の肥大化した CLAUDE.md（または Before/After 図）

### 3. Skills とは何か — 30秒で理解する（600字）
- 定義：**特定タスクのために LLM に「いつ・どう動くか」を教える `.md` ファイル群**
- 仕組み図：`description` をトリガーにLLMが自動で読み込む
- ファイル構成（`SKILL.md` + 補助ファイル）
- スコープ：プロジェクト Skill / ユーザー Skill / プラグイン Skill の違いを表で比較

### 4. 実践：自分専用 Skill を作ってみる（2,000字）
題材：**「Zenn記事のフロントマターを自動生成・検証する Skill」**（CLAUDE.md と相性の良い実例）

- ステップ1：`.claude/skills/zenn-frontmatter/SKILL.md` を作る
- ステップ2：`description` の書き方（トリガー精度を上げるコツ）
- ステップ3：手順を書く（命令ではなく "判断材料" を渡す）
- ステップ4：補助スクリプト（`scripts/validate.sh`）を同梱する
- 実際に呼び出した動作ログ（コードブロック）

### 5. 一段上の使い方：チームで Skills を運用する（1,500字）
- **パターンA**：プロジェクト直下の `.claude/skills/` で Git 管理 → PR レビュー対象にする
- **パターンB**：社内向けプラグイン化して横展開する
- 命名規則・description 設計のチームルール例
- 「Skill 同士が衝突したらどうなるか」の検証結果

### 6. ハマりどころ・実戦TIPS（1,000字）
- ❌ description が曖昧で発火しない → ◎ トリガーワードを箇条書きで列挙
- ❌ 手順を書きすぎてLLMが従わない → ◎ "Why" と判断基準だけ書く
- ❌ Skill 内から別 Skill を呼びたい → 現状の制約と回避策
- バージョン管理：Skill 自体を更新したときの動作確認手順

### 7. CLAUDE.md / MCP / サブエージェント との使い分け（700字）
- 比較表：何を入れる場所か（永続知識 / 外部接続 / 手順 / 専門役割）
- 「Skills に入れるべきでないもの」のチェックリスト
- 自分の運用でたどり着いた使い分けルール

### 8. おわりに（400字）
- まとめ：Skills は **「AIに渡す作業の関数化」**
- Next Step：読者が今日できる最小アクション3つ
  1. 既存の CLAUDE.md から手順部分を Skill に切り出す
  2. よく使うプロンプトを1本だけ Skill 化してみる
  3. チームの `.claude/skills/` を Git 管理に入れる
- 今後の展望：Anthropic 公式の Skill エコシステム化への期待
- 謝辞・参考リンク（Anthropic 公式ドキュメント、関連記事）
