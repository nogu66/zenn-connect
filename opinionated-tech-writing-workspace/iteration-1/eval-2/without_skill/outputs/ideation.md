# MCPサーバー自作経験を記事化するための壁打ち

「MCPサーバーを作った」という事実だけでは記事になりません。**「誰の・どんな問題を・どう解いたか」** に絞り込むことで、初めて読者に届く記事になります。以下の質問とテーマ案を使って、軸を1つに決めましょう。

---

## まず最初に答えてほしい7つの質問

テーマを絞るために、以下を順番に答えてみてください。回答内容によって最適な記事の型が変わります。

### Q1. なぜ「自作」したのか？（動機）
- [ ] 既存のMCPサーバーが存在しなかった
- [ ] 既存のものはあったが、機能・性能・思想が合わなかった
- [ ] 学習目的・素振り
- [ ] 業務の特定ワークフローを自動化したかった
- [ ] その他（自由記述）

→ **ここが記事の「Why」になります。** 「なかったから作った」のか「あったけど不満だったから作った」のかで、記事の説得力の作り方が変わります。

### Q2. そのMCPサーバーは何をするものか？（一文で）
例：「Notionのデータベースを検索してClaudeに渡す」「社内のJira APIをラップする」「ローカルのDuckDBに自然言語でクエリする」

→ **一文で言えないなら、スコープが広すぎる可能性があります。** 一文化できるまで切り詰めるのが先決です。

### Q3. 作る前に何で困っていたか？（Before）
- 何分／何時間かかっていた作業？
- 手作業でのコピペ・転記が発生していた？
- Claude Codeに毎回コンテキストを貼り付けていた？
- 既存ツールのどこが「微妙に」不便だった？

→ **記事の冒頭で読者を引き込む「あるある」になります。**

### Q4. 作った後、何が変わったか？（After）
- 定量的な変化（時間短縮、エラー削減、リクエスト数）
- 定性的な変化（思考の流れが途切れなくなった、など）

→ **数字 or 体験談で語れると記事の信頼性が跳ね上がります。**

### Q5. 一番ハマった・苦労したポイントは？
- プロトコル仕様の理解
- Tool定義のスキーマ設計
- 認証・認可（OAuth、トークン管理）
- ストリーミング／非同期処理
- エラーハンドリング
- Claude Desktop／Claude Codeとの接続デバッグ
- その他

→ **「ここで2時間溶かした」みたいな話が、最も読まれる部分になります。**

### Q6. 想定読者は誰か？
- [ ] MCPをまだ触ったことがない人（入門記事になる）
- [ ] MCPは知ってるが自作したことはない人（チュートリアル記事になる）
- [ ] 既に自作したことがある中級者（設計論・運用論記事になる）
- [ ] 特定ドメイン（例：データ分析、社内ツール開発者）の人

→ **読者層によって、解説する深さと省略する前提が180度変わります。**

### Q7. 公開してどうなりたいか？
- [ ] 同じ問題で詰まっている人を救いたい
- [ ] OSSとして使ってもらいたい（記事はプロモーション）
- [ ] 自分の理解を整理したい
- [ ] 採用・案件獲得につなげたい

→ **ゴールによってCTA（最後の誘導）が変わります。**

## 想定される記事テーマの方向性（5案）

Q1〜Q7の答えがぼんやりしている段階でも、以下のどれが「一番自分の経験にフィットするか」を直感で選んでみてください。

### A. 「課題解決ストーリー型」（最もZennで読まれやすい）
> **タイトル例**：「毎日10分のNotion検索が辛かったので、MCPサーバーを自作してClaude Codeに任せたら3秒になった」

- 構成：Before（困りごと）→ なぜ既存ツールでは解けなかったか → 自作の設計判断 → After（実測値）→ 学び
- 向いている人：Q3とQ4が具体的に語れる人
- 強み：再現性が高く、読者が自分ごと化しやすい

### B. 「ハマりポイント全部書く型」
> **タイトル例**：「MCPサーバーを自作して詰まった7つのポイントと解決策」

- 構成：各ハマりポイントごとに「症状 → 原因 → 解決」を並べる
- 向いている人：Q5に複数のエピソードがある人
- 強み：検索流入が強い。同じエラーで困った人が必ず辿り着く

### C. 「設計判断の言語化型」（中級者向け、刺さる人には深く刺さる）
> **タイトル例**：「MCPサーバーのTool粒度はどう設計すべきか — 自作して見えてきた3つの原則」

- 構成：原則の主張 → 自作経験での反例・成功例 → 実装の差分
- 向いている人：Q1で「既存のものに不満があった」と答えた人
- 強み：他の記事と差別化しやすい。エンジニアコミュニティで議論を呼ぶ

### D. 「ハンズオン入門型」
> **タイトル例**：「Pythonで作る最小のMCPサーバー — Claude Codeから自作ツールを呼ぶまで」

- 構成：環境構築 → Hello World → 機能追加 → デバッグ → 公開
- 向いている人：Q6で「未経験者向け」を選んだ人
- 強み：ストック記事として長く読まれる
- 注意：**公式ドキュメントの劣化コピーにならないよう、自分の躓きと工夫を必ず混ぜる**

### E. 「ドメイン特化ユースケース型」
> **タイトル例**：「社内Slackの過去ログをClaudeに食わせるMCPサーバーを作った話 — RAGとの違いと使い分け」

- 構成：ドメイン課題 → MCPで解いた理由（vs 他の選択肢）→ 設計 → 運用上の知見
- 向いている人：特定の業務／ドメインに紐づいた経験がある人
- 強み：競合記事が少なく、専門性で評価されやすい

## テーマ絞り込みのための3ステップ

### Step 1: 「自分が3ヶ月前に読みたかった記事」を1行で書く
書けないなら、まだ書く時期ではない可能性があります。経験を3日寝かせてから戻ってきましょう。

### Step 2: 既存記事のリサーチ（30分でいい）
- Zennで `MCP` `MCPサーバー` `Model Context Protocol` で検索
- Qiita、個人ブログ、英語圏（dev.to、Medium）も軽く
- **「自分の経験で、まだ誰も書いていない切り口」を1つ見つける**
- 既に同じ切り口の記事がある場合 → より具体的・より個人的にズラす

### Step 3: 仮タイトルと冒頭3行だけ書いてみる
本文より先にこれを書いて、自分でワクワクするか確認する。ワクワクしないなら切り口がズレています。

## 次のアクション（ユーザーへの依頼）

上記の **Q1〜Q7に箇条書きで答えてください**。回答が揃った段階で：

1. A〜Eのどの型が最適か確定する
2. 仮タイトル3案を出す
3. 章立て（目次）を一緒に作る
4. 冒頭の「はじめに」セクションを書き始める

までを一気に進められます。

特に **Q3（Before）とQ5（ハマりポイント）** が記事の心臓部です。ここに書ける具体的なエピソードが多いほど、強い記事になります。
