# MCPサーバー自作の経験を技術記事にする — 壁打ちパッケージ

「テーマがぼんやり」段階を抜けるには、**主張1行（Hill I will die on）と読者像**を先に固めるのが最短ルートです。書き始める前にここを決めれば、残りの執筆は3倍速くなります。

以下、Specベース執筆ワークフロー（フェーズ1）に沿って進めます。

---

## ステップ1: まず答えてほしい質問（5つ）

主張1行と読者像を絞り込むため、以下に答えてください。完璧でなくて構いません。**思いつきの一言でOK**。

### Q1. その MCPサーバーは「何を解決するため」に作りましたか？
- 既存の MCP サーバーで満たせなかったニーズは何でしたか？
- 「自分が困っていたこと」を一言で言うと？
- 例: 「Notion の DB を Claude から自然言語で更新したかった」「社内 Slack のスレッドを Agent に要約させたかった」

### Q2. 作ってみて「これは譲れない」と思った気づきは何ですか？
- 作る前と後で、自分の MCP / Agent 設計の考え方がどう変わりましたか？
- 「もう昔のやり方には戻れない」と感じたポイントを1つだけ挙げるなら？
- 例: 「MCPサーバーは tool を増やすより resources を活用すべき」「自作する前に公式 SDK のサンプルを完コピしろ」「ツール設計の良し悪しが Agent の精度を決める」

### Q3. 一番ハマった失敗・落とし穴は何ですか？（数値があれば最高）
- 何時間／何日溶かしましたか？
- 公式ドキュメントには書いていなかった注意点は？
- 例: 「stdio と SSE の使い分けで2日溶かした」「tool description を雑に書いて Agent が誤呼び出しを連発した」

### Q4. 想定読者は誰ですか？（具体的に1人を思い浮かべて）
- その人は今、どこで詰まっていますか？
- 「半年前の自分」だとしたら、当時の自分は何で困っていましたか？
- 例: 「MCP のドキュメントを読んだけど何から作ればいいか分からないエンジニア」「公式サンプルは動かせたけど、自分のユースケースに落とし込めない人」

### Q5. その MCPサーバーは「人に見せられる状態」ですか？
- 公開リポジトリ／スクリーンショット／実行ログはありますか？
- 本番運用していますか？社内ツール？個人用？
- 「まだ試している最中」でも全然OK（むしろ正直に書いた方が刺さります）

## ステップ2: 仮の回答に基づく Spec 例

たとえば Q1〜Q5 の回答が以下だったとします（**あくまで例**。実際の答えで上書きしてください）：

> Q1: Zenn の記事メタデータ（frontmatter）を Claude から直接編集できる MCP サーバーを作った
> Q2: tool description は「Agentへのプロンプト」だと気づいた瞬間、設計の考え方が180度変わった
> Q3: tool 名を雑に `update` にしたら、Agent が他のツールと混同して誤呼び出しを連発。3日溶かした
> Q4: 公式の Quickstart は動かせたが、「自分のユースケースに合わせて作り直す」段階で詰まっているエンジニア
> Q5: GitHub に公開済み。自分の Zenn 執筆フローで2週間運用中

これを元にした Spec の骨子はこうなります。

### 主張1行（Hill I will die on）

```
MCP サーバーの tool description は「Agent への運用プロンプト」だ。
ここを雑に書くと、どれだけツールを足しても Agent は壊れる。
```

> 自問チェック: 「〜について解説します」になっていない ✅／友人に話したら反論／納得が来そう ✅

### 想定読者（3行）

```
- 誰: 公式 Quickstart で MCP サーバーを動かせたエンジニア（Python/TS の基礎あり）
- 今困っていること: 自作 MCP サーバーを Agent に繋いだが、tool が呼ばれない／誤呼び出しが多い
- 読後に変わること: tool description の書き方を見直し、誤呼び出し率が下がる手応えを得る
```

### 伝えたいこと（10項目の例）

ここは本来 20〜40 個出します。**まずは10個出してみて、増やせなければリサーチ不足のサイン**です。仮例：

1. tool description は Agent に対する自然言語プロンプトであり、API ドキュメントではない
2. tool 名を `update` のような汎用語にすると、他ツールと衝突して誤呼び出しが起きる（自分の3日溶かした失敗談）
3. description に「いつ使うべきか／いつ使わないべきか」を必ず両方書く
4. 引数の例を description 内に直書きすると、Agent の引数生成精度が体感で上がる
5. resources と tools の使い分け — 「読み取り専用は resources に寄せる」が自分の結論
6. stdio / SSE / HTTP の選択基準（ローカル単発 vs 共有運用）
7. Claude Desktop でのデバッグ手順（ログの場所、`claude_desktop_config.json` の罠）
8. 公式 SDK（Python / TypeScript）のサンプルから始めるべき理由
9. 自作 MCP の Zenn 執筆フロー実例（GitHub リポジトリへのリンク）
10. Next Step: 既存の自作 MCP の tool description を3つだけリライトして、Agent の挙動を比較する

> Spec 上はここから20項目まで増やすのが目標。失敗談・比較・数値・コード例・スクリーンショット候補のカテゴリで穴埋めしていくと自然に増えます。

## ステップ3: ここから先の進め方

Spec が固まったら、以下の順で進めます。

### 3-1. タイトル候補を3つ出す（トーン違い）

主張1行が決まれば、タイトルは派生で書けます。**強硬／中庸／謙虚の3トーン**で出して、最後に1つ選ぶ。

仮例（上記 Spec ベース）:

- **強硬**: 「MCP の tool description を雑に書いている人は、全員 Agent を壊している」
- **中庸**: 「MCP サーバー自作で気づいた、tool description が Agent 精度を決める話」
- **謙虚**: 「MCP サーバーを2週間運用してわかった、tool description の書き方メモ」

> 強硬版は刺さるが好き嫌いが分かれます。中庸版は安全。**Zenn なら中庸〜強硬**、X 用なら強硬がよく伸びます。

### 3-2. 冒頭1文（Hill を文章化）

例:
> MCP サーバーを自作して2週間。確信した — **tool description は Agent への運用プロンプトだ**。ここを雑に書くと、ツールをいくら増やしても Agent は壊れる。

### 3-3. 7段構造への振り分け

Spec の10〜20項目を、以下の枠に振り分けます。

| セクション | 入れる素材 |
|---|---|
| ① 冒頭（Hill） | 主張1行 + 個人の確信 |
| ② 問題提起 | 「Agent が tool を呼ばない／誤呼び出し」の具体シーン |
| ③ Why の深掘り | 失敗談（3日溶かした話）+ 比較（雑な description vs 改善後）+ 数値（誤呼び出し率の体感差） |
| ④ How | description の書き方テンプレ（いつ使う／いつ使わない／引数例） |
| ⑤ 実例 | GitHub リポジトリ + Claude Desktop のスクショ + 実行ログ |
| ⑥ 注意点 | tool 名の衝突／stdio vs SSE の罠／Claude Desktop の config パス |
| ⑦ Next Step | 「既存の自作 MCP の tool description を3つだけリライトして比較してみてください（10分）」 |

### 3-4. 書き始める前のチェック

- [ ] 主張1行を、声に出して言ってみる。**本当に死ぬほど信じているか？**（半信半疑なら主張を弱めるか、テーマを変える）
- [ ] 想定読者の「読後に変わること」と Next Step が一致しているか？
- [ ] 自分の実例 or 「試している最中」と正直に書ける素材があるか？
- [ ] 数値 or 体感差を1つ以上、Why に入れられるか？

ここまで通ったら、本文執筆フェーズに入れます。
