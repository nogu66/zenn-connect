# 書き直し案

## 案A：強硬トーン（断定・一人称・実体験）

### はじめに

Claude Code Skills を使い始めて1ヶ月、もうSystemプロンプトに長文を詰める運用には戻れない。

「Claudeに同じ手順を毎回貼り付ける」「プロジェクトごとにプロンプトをコピペで管理する」——半年前の僕が毎日やっていたことだ。Skillsはこの運用を根本から壊す。手順を `.claude/skills/` に1ファイル置くだけで、Claudeが必要な時だけ読み込み、必要ない時はコンテキストを汚さない。手元の体感では、繰り返し作業のセッション開始時のトークン使用量がざっくり半分以下になった。

この記事は「Skillsの便利さ」を紹介するものではなく、**「Systemプロンプト中心の運用はもう捨てていい」と僕が確信するに至った理由**を書く。読み終えたら、あなたが今Notionや`CLAUDE.md`に書き溜めている手順のうち、最低1つはSkill化したくなっているはずだ。

---

### 何を変えたか（差分の解説）

**ビフォー（弱い理由）**
- 「Skillsは〜機能です」 → 公式ドキュメントの冒頭と同じ。中立紹介で個人の熱量がゼロ。
- 「この記事ではSkillsの使い方を解説します」 → 原則1違反。「解説します」は『Hill I will die on』の真逆。
- 「効率化できます。便利なので、ぜひ試してみてください」 → 抽象・伝聞・社交辞令。Whyがゼロ。読後の行動につながらない。

**アフター（強い理由）**
- **冒頭1文を「Hill I will die on」化**：「Skillsを使い始めて1ヶ月、もうSystemプロンプトに長文を詰める運用には戻れない」。期間（1ヶ月）と一人称（戻れない）と断定が同居している（原則1）。
- **Whyを失敗談で先出し**：「半年前の僕が毎日やっていた」と過去の自分を引き合いに出し、対比で「Skillsはこの運用を壊す」と続ける（原則2・3）。
- **数値で裏付け**：「トークン使用量がざっくり半分以下」を体感値として明記。数値が出せる時は出す、出せない時は「体感」と正直に書く（原則2）。
- **記事の宣言を「How」から「Why」へ移す**：「使い方を解説します」ではなく「確信するに至った理由を書く」。読者が一番欲しいものはWhyだ（原則2）。
- **読者の変化を予告**：「読み終えたらSkill化したくなっているはず」と読後の状態を約束する（原則5の予告）。

## 案B：中庸トーン（控えめだが確信は手放さない）

### はじめに

正直、最初は「Skillsって、結局プロンプトをファイル分割しただけじゃないの？」と思っていた。

でも実際に2週間、自分の業務で使い込んでみて考えが変わった。Claude Code Skills は「ファイル分割」ではなく、**「Claudeに渡す知識を、必要な時だけロードする仕組み」**だ。Systemプロンプトに全部詰める運用と比べると、コンテキストの使い方が根本的に違う。

この記事では、僕がSkillsに乗り換えた理由を、最初に踏んだ落とし穴と一緒に書く。手順だけ知りたい人は公式ドキュメントを読めば十分なので、ここでは**「なぜSystemプロンプト中心の運用から離れたのか」**だけに絞って書きたい。

読み終わった頃には、今あなたがCLAUDE.mdに書き溜めている手順のうち、Skill化したほうがいいものが何個かは見えているはずだ。

---

### 何を変えたか（差分の解説）

**ビフォー（弱い理由）**
- 「便利な機能なので、ぜひ試してみてください」 → 中立かつ社交辞令。読者の心が動かない。
- 「Skillsを使うことで、繰り返し使う手順を効率化できます」 → 「効率化」は抽象語の典型。何がどう変わるかゼロ。
- 全体として「書き手がこの技術にハマっている」気配がない。

**アフター（強い理由）**
- **半信半疑からの転向ストーリー**で始める：「最初は〜と思っていた」→「考えが変わった」（原則6：人間味）。強硬主張が苦手な読者にも刺さる入り方。
- **Skillsの定義を「自分の言葉」で言い直す**：公式の「手順書を追加できる機能」ではなく、「必要な時だけロードする仕組み」と言い換える。これが書き手の解釈であり、価値の核（原則2のWhy）。
- **記事のスコープを明示して捨てる**：「手順だけ知りたい人は公式を読めばいい」と切り捨てる勇気。これによって残った読者にWhyが深く刺さる（原則4：1セクション1アイデア）。
- **謙虚だが確信は手放さない**：「絶対やるべき」ではなく「Skill化したほうがいいものが見えているはず」。トーンは穏やかでも、読後の行動を予告している（原則5）。
- **「2週間使い込んだ」という時間軸**で実体験性を担保（原則3）。

## 案C：謙虚トーン（実験中の正直さで信頼を取りにいく）

### はじめに

Claude Code Skills について書こうとして、最初に手が止まった。

「使い方を解説する記事」なら30分で書ける。でもそれを書いて、自分が今までに何度ガッカリしたか思い出した——「○○の使い方」とタイトルにある記事を読んで、結局公式ドキュメントの劣化版だったときの、あの徒労感だ。

だからこの記事は、Skillsの仕様紹介はしない。代わりに、**僕が実際に1ヶ月Skillsを運用してみて、Systemプロンプト中心の書き方をどう捨てていったか**——その途中経過を書く。本番投入というほど大規模ではない。個人の執筆ワークフローと小さな業務スクリプトに使った範囲だ。それでも、戻る気はもうしない。

完璧な答えではなく、僕が今いる地点を共有する。同じように「CLAUDE.mdが膨らみすぎて辛い」と感じている人にだけ届けばいい。

---

### 何を変えたか（差分の解説）

**ビフォー（弱い理由）**
- 「この記事ではSkillsの使い方を解説します」 → まさにこの「解説します」型を、書き手自身が一番憎んでいる、という構造を捨てている。記事のメタ視点がゼロ。
- 「ぜひ試してみてください」 → 誰に向けた言葉なのか不明。

**アフター（強い理由）**
- **「書こうとして手が止まった」というメタ視点**で入る（原則7：メタ技法も惜しまず公開）。書き手の執筆プロセスを共有することで、読者は「この人は中身のないことは書かない」と判断できる。
- **「使い方解説」を自分で否定する**：「○○の使い方」記事でガッカリした経験を共有することで、この記事のスコープを差別化する（原則1：強い主張は静かに書く方が伝わる、の体現）。
- **実験中の正直な記述**：「本番投入というほど大規模ではない」と先回りで誠実に書く。原則3の「実例がまだ少ないなら『今試している最中』と正直に書く方が信頼される」を直接適用。
- **読者を絞る勇気**：「『CLAUDE.mdが膨らみすぎて辛い』と感じている人にだけ届けばいい」。万人受けを捨てる方が、刺さる読者には深く刺さる（原則1）。
- **「戻る気はもうしない」という静かな確信**：強い断定はしないが、確信の核はちゃんと置く。謙虚トーンでも『Hill I will die on』は失わない。

---

## 3案の使い分け

| 案 | トーン | こんな時に向く |
|----|--------|--------------|
| A：強硬 | 断定・熱量MAX | X発信込みでバズらせたい／読者層が中上級者 |
| B：中庸 | 半信半疑→転向 | Zenn王道。広く読まれることを狙う |
| C：謙虚 | 実験途中の共有 | 自分がまだ試行錯誤中／信頼ベースで届けたい |

迷ったら**案B**を推す。Zennの読者層と相性が良く、原則1〜7のうち6つを満たしながら、強硬すぎて読者を選ぶリスクを避けられる。
