# 書き直し案

## 案1: 強い断定型（Hill I will die on スタイル）

### はじめに

**Claude Code Skillsを「便利な機能」として紹介する記事は、もう要らない。**

Skillsの本質は「手順書の追加機能」ではなく、**Claudeに対するあなたの暗黙知を、組織の資産として外部化する装置**だ。私はこの3ヶ月でSkillsを20個以上書いてきたが、断言できる。Skillsを「効率化ツール」として使っているうちは、その価値の半分も引き出せていない。

なぜか。Skillsを真に強力にするのは「繰り返しを減らす」ことではなく、**「Claudeが自律的にいつ・どの手順を発動すべきかを判断する」**点にある。これは従来のスニペットやテンプレートとは根本的に違う発想だ。

この記事では、この立場から以下を扱う。

- なぜ「便利機能」フレームでSkillsを語ると失敗するのか
- 私が実際に運用して見えた、効くSkillsと効かないSkillsの分かれ目
- 今日から書ける、最初の1個のSkillの設計

「Skillsの使い方を知りたい」だけの人には、公式ドキュメントを勧める。この記事は、**Skillsを自分のチームの中核に据えたい人**のためのものだ。

---

### この案で変えたこと

- **冒頭1行を「敵を定義する宣言」に置換**: 「便利な機能」という凡庸なフレーミングを名指しで否定し、立場を明確化
- **筆者の実体験を数値で挿入**: 「3ヶ月で20個以上書いた」という具体性で、書き手の信頼性を担保
- **Whyを2層で深掘り**: 「効率化」という表層的Whyを否定 → 「自律的判断」という本質的Whyに到達
- **読者を選別**: 「公式ドキュメントを勧める」と切り捨てることで、対象読者を鋭く絞り込む
- **「便利な機能なので試してみてください」という弱い結語を削除**: 行動喚起は記事末で具体的Next Stepとして再設計する前提

## 案2: 問題提起型（落ち着いた論証トーン）

### はじめに

Claude Code Skillsの解説記事を10本ほど読んで、私はある違和感に気づいた。**どの記事も「Skillsはこう書ける」を語るが、「いつSkillsを書くべきか」を語らない。**

この違いは、実運用では決定的だ。

私が最初に書いたSkillは、3日で使われなくなった。手順は正しく、コードも動いた。にもかかわらず使われなかった理由はひとつ — **Claudeがそのスキルを「発動すべきタイミング」を判定できない設計だったから**だ。Skillsは命令文の集合体ではない。**Claudeが文脈から自律的に呼び出すための、判定可能な記述**である必要がある。

この視点が抜けたまま書かれたSkillsは、SKILL.mdというファイル名のメモ帳に過ぎない。

本記事では、この前提に立った上で次を扱う。

1. Skillsが「発動されない」最頻出の原因
2. description欄の書き方が、機能のすべてを決める理由
3. 自分の手元で動くSkillを1つ作るまでの最短ルート

対象読者は「Skillsを試したが期待通りに発動しなかった人」「これから本格的に運用したい人」だ。Skillsの存在を初めて知った段階の人は、まず公式ドキュメントを2〜3分眺めてから戻ってきてほしい。

---

### この案で変えたこと

- **筆者の失敗談を冒頭に配置**: 「3日で使われなくなった」という具体的失敗で読者を引き込む
- **「Whatではなくwhen」という対立軸を提示**: 既存記事との差別化点を明示し、本記事を読む理由を作る
- **太字での主張埋め込み**: 流し読みでも論旨が伝わる構造に
- **「便利」「ぜひ」という曖昧語を全削除**: 主張の強度を下げる修辞を排除
- **対象読者と非対象読者を明示**: 「初めての人は公式ドキュメントへ」と誘導することで記事の密度を担保
- **トーンは案1より控えめ**: 断定よりも「気づき → 仮説 → 検証」の論証構造で、技術者層に刺さる落ち着きを優先

## 案3: 逆張り・挑発型（カジュアル・短文リズム）

### はじめに

Skillsを「Claudeに手順書を覚えさせる機能」だと思っているなら、たぶん使いこなせない。

これは煽りではなく、**設計思想の話**だ。

手順書は「人間が読んで実行する」ことを前提に書かれている。一方Skillsは、**Claudeが「読むべきか・今読むべきか」を自分で判断する**ことを前提に書かれる。この一段ズレた抽象を理解しないまま書くと、Skillsは沈黙する。動かないのではなく、呼ばれない。

私もこのズレで2週間溶かした。だからこの記事を書いている。

- 第1章: なぜあなたのSkillは呼ばれないのか
- 第2章: descriptionは「機能名」ではなく「発動条件」だ
- 第3章: 動くSkillを15分で1つ作る

公式ドキュメントの和訳が欲しい人には向かない。**自分のSkillが想定通り動かなくてイラついている人**に届けたい。

---

### この案で変えたこと

- **1文目を逆説で始める**: 「便利」と真逆の「使いこなせない」で読者の手を止める
- **短文リズムでテンポ感を出す**: Zenn読者の流し読み速度に合わせて、改行を多用
- **「2週間溶かした」という生々しい数字**: 共感の入口として失敗の重さを定量化
- **「沈黙する」「呼ばれない」という比喩**: 抽象概念を擬人化して記憶に残す
- **対象読者を感情で絞る**: 「イラついている人」と感情ベースで読者を呼び込む
- **章立てを冒頭で予告**: カジュアルなトーンでも構造が見える設計に
